## Обзор продукта

### Что это

Сервис защиты клиентских сайтов от ботов и абьюза, работающий на proxy-слое CDN. Стоит на пути HTTP-трафика перед origin клиента: каждый входящий запрос проходит через цепочку проверок и получает вердикт — пропустить, заблокировать или отправить на верификацию — еще до того, как достигнет сайта клиента.

Цель — отсекать вредный автоматизированный трафик (скрейперы, брутфорс, сканеры, DDoS-боты), не мешая живым пользователям и легитимным ботам (поисковики, мониторинги, платежные webhook'и).

### Из чего состоит

Две части с разделением ответственности: proxy принимает решения по трафику, backend снабжает proxy данными и собирает результаты.

#### Proxy (nginx + Lua)

Слой на пути трафика, где выполняется весь каскад проверок — синхронно, в hot-path, за микросекунды, до того как запрос уйдет на origin клиента. Все данные для решений лежат локально в памяти, без сетевых вызовов на сторону во время обработки запроса.

#### Backend

Серверная часть, отдельная от proxy и вне hot-path. Запрос пользователя ее никогда не ждет. Несет три функции:

- Catalog server — хранит и раздает на proxy каталоги (списки плохих IP, паттерны ботов, TLS-сигнатуры, политики доменов и т.д.), которые proxy кэширует у себя локально.
- Приемник логов — собирает структурированные логи со всех proxy-узлов, обогащает и складывает в телеметрию для аналитики.
- rDNS-воркер — фоном проверяет, что IP, представившиеся поисковыми ботами, действительно им принадлежат (защита SEO).

Если backend недоступен — proxy продолжает работать на последних загруженных каталогах, трафик не страдает.

### Что такое «каскад»

Каскад — это упорядоченная цепочка слоев проверки, через которую проходит каждый запрос, по принципу «дешево — первым»: легкие проверки раньше, дорогие позже. Запрос идет по слоям, пока какой-то слой не вынесет терминальный вердикт (заблокировать либо пропустить по фастпасу) или пока не дойдет до конца.


| Слой                 | Что проверяет                                                                                   |
| -------------------- | ----------------------------------------------------------------------------------------------- |
| L1 — Hygiene         | Базовая гигиена: HTTP-метод, черный список User-Agent                                           |
| L2 — Reputation      | Репутация источника: IP (списки), ASN, гео, подтвержденные боты, clearance-cookie               |
| L3 — TLS-fingerprint | Сигнатура TLS-стека клиента — распознает автоматизированных клиентов, маскирующихся под браузер |
| L4 — Rate-limits     | Поведение во времени: частота запросов по разным ключам (IP, IP+UA, TLS-fp, уникальные URL)     |
| L5 — Verification    | Активная верификация: JS-challenge для браузеров, блок для не-браузерных клиентов               |


Внутри слоя проверки выполняются отдельными правилами. Правило (rule) — это одна именованная проверка с условием и категорией (например, «метод не в whitelist», «IP в блок-листе», «несоответствие TLS-сигнатуры заявленному браузеру»). При срабатывании правило либо выносит вердикт (заблокировать или пропустить по фастпасу), либо помечает запрос флагом. У каждого правила есть короткий идентификатор (например, `ip_blocklist`), который записывается в лог — по нему видно, какое именно правило сработало.

Флаг (challenge-флаг) — это пометка на запросе «выглядит подозрительно, кандидат на верификацию». Сам по себе флаг не блокирует и не пропускает запрос: пометки копятся по ходу каскада, а окончательное решение по ним принимается на финальном слое L5. Так устроены «мягкие» (soft) правила — например, признаки автоматизации в TLS-сигнатуре помечают запрос флагом, а не блокируют сразу.

Кроме правил есть теги. Тег тоже срабатывает по условию, но, в отличие от правила, ни на вердикт, ни на верификацию не влияет — он только описывает запрос (например, «IP из датацентра») и копится в `tags` для аналитики. То есть правило влияет на судьбу запроса (вердиктом или флагом), а тег лишь помечает его.

Накопленные флаги консолидируются на финальном слое L5 — он решает, отправлять ли запрос на верификацию. Каждый запрос на выходе дает ровно одну запись лога с финальным вердиктом и всеми сработавшими сигналами (правилом, флагами, тегами).

### Каталоги, политики и режимы

Данные, по которым работает каскад, бывают двух видов:

- Общие каталоги — ведет продакт, действуют сразу на всех клиентов: списки плохих IP, паттерны плохих User-Agent, ASN датацентров, TLS-сигнатуры известных ботов и автоматизации. Обновляются через PR по результатам анализа логов.
- Политики клиентов (policy) — настройки отдельного домена, влияют только на него и не затрагивают других клиентов.

Политика домена включает: режим работы, пороги срабатывания правил, кастомные правила клиента (свои паттерны UA, блокировки по ASN, лимиты по путям), список доверенных IP, тоггл усиленной защиты.

Режимы работы:

- shadow — каскад считает и логирует вердикт, но физически ничего не блокирует. Используется для наблюдения и калибровки на реальном трафике.
- active — вердикты исполняются (блок или challenge).
- attack_mode (Under Attack) — аварийный тоггл для домена: под атакой все, что дошло до верификации, отправляется на challenge.

### Кому это нужно

- Сайт получает нагрузку от ботов и сканеров — медленнее работает, растет счет за хостинг
- Форма логина или регистрации перебирается брутфорсом
- API перегружается нелегитимными запросами
- Страница поиска или каталог скрейпится конкурентами
- Периодические всплески трафика (атаки, внезапные упоминания) кладут origin

### Чем не является

Это базовая защита, не enterprise-решение класса Cloudflare Bot Management или DataDome. Сервис не справится с:

- Продвинутыми ботами, которые эмулируют поведение браузера (Puppeteer/Playwright со stealth-режимом)
- Residential proxy-сетями (трафик идет с легитимных домашних IP)
- Ботами, которые целенаправленно адаптируются под наши проверки
- Поведенческим анализом сессий

Продукт покрывает ~80% типичных abuse-сценариев для малого и среднего бизнеса.

## Режимы работы

У каждого сайта два режима: shadow (по умолчанию, бесплатно) и active (платно, с реальными блокировками). Это же поле — `mode` в per-resource policy. 

### Shadow *(по умолчанию, для всех)*

Каскад наблюдает за трафиком и пишет вердикты в лог, физических действий с запросом нет. Клиент видит в дашборде аналитику бот-трафика («у вас X% запросов выглядят как боты»), но реальной защиты пока нет.

Это режим по умолчанию для каждого нового edge-домена и для всех бесплатных клиентов. Включается автоматически без действий клиента.

Для нас это монетизационный hook: показываем клиенту, что мы видим в его трафике, и продаем active-режим.

### Active *(платно)*

Полноценная защита: блокирующие правила реально блокируют (403 / 429 с Retry-After), soft-сигналы триггерят верификацию через L5 (JS challenge), верифицированные краулеры фастпасят. Все то, что в shadow было «бы заблокировано» — теперь реально блокируется.

Внутри active есть аварийный тоггл Under Attack mode (`attack_mode=true`) — per-host, клиент включает его для своего домена. При его включении на L5 форсится `should_challenge()=true` для всех запросов, дошедших туда: браузеры идут на JS challenge, non-browser клиенты блокируются как `non_browser_blocked` (Ветка B), протокольно несовместимые запросы — как `unchallengeable_request` (Ветка C). Verified search bots и держатели IP-whitelist'а продолжают фастпасить на L2 (SEO/доверенные интеграции не страдают). Clearance cookie, выданные ДО начала атаки, во время `attack_mode=on` не фастпасят (атакующий мог накопить их заранее) — такой запрос идет через каскад до L5 на challenge. Cookie, выданные уже во время атаки (после перепрохождения challenge), фастпасят как обычно, поэтому реальный пользователь проходит challenge один раз за атаку, а не на каждом запросе. Использовать при идущей атаке или превентивно перед ожидаемой нагрузкой.

## Слои защиты — пирамида L1–L6

Принцип каскада: каждый следующий слой дороже и/или богаче состоянием. Дешевые проверки — первыми, чтобы плохой трафик отсекался максимально рано и не тратил ресурсы.

L-номера в этой таблице — визуальная иерархия слоев по сложности и стоимости. В тексте каскада ниже и в JSON-логе мы используем имена стейджей (`hygiene`, `reputation`, `tls_fp`, `rate_limits`, `verification`) — они едины везде. L-номер можно воспринимать как «номер слоя в пирамиде», имя стейджа — как «код этапа в коде и в логе».


| Слой   | Stage                      | Сигнал                                                                                                              | Стоимость          | Состояние                                                          | Где                                 |
| ------ | -------------------------- | ------------------------------------------------------------------------------------------------------------------- | ------------------ | ------------------------------------------------------------------ | ----------------------------------- |
| **L1** | `hygiene`                  | Метод whitelist, UA-blacklist                                                                                       | nanosec            | static config                                                      | proxy                               |
| **L2** | `reputation`               | Clearance cookie verify (HMAC), Verified-bot allowlist (rDNS), IP whitelist/blocklist, ASN customer/datacenter, Geo | μs                 | HMAC stateless + static lists + MaxMind + rDNS verdicts из backend | proxy                               |
| **L3** | `tls_fp`                   | Fingerprint compute, fp blocklist, impersonator, suspicious ciphers                                                 | ~μs                | catalog + per-fp cache                                             | proxy (compute) + backend (catalog) |
| **L4** | `rate_limits`              | per-IP, per-IP+UA, per-API, per-fp, rate_scan_urls — sliding 10s/60s                                                | μs                 | per-proxy counters                                                 | proxy                               |
| **L5** | `verification` *(roadmap)* | JS challenge issuance, clearance cookie issue, Under Attack mode                                                    | sec issue          | HMAC secret stateless                                              | proxy (issue)                       |
| **L6** | *(out of scope v1)*        | Mouse, timings, sequence URLs — поведенческий ML на сессиях                                                         | требует JS-биакона | full sessions                                                      | future                              |


**v1 = L1–L5.** L6 — это уже другой продукт.

**Контракт stage-кодов: стабильны между итерациями.** Если в будущем появится новый слой каскада, он получит новый stage-код, а существующие (`hygiene`, `reputation`, `tls_fp`, `rate_limits`, `verification`, `egress`) не переименовываются и не сдвигаются. Это нужно чтобы старые логи и аналитика по ним оставались интерпретируемыми после любых расширений.

## Как это работает

End-to-end разбор по этапам обработки запроса — от приема после TLS-handshake через слои каскада до доставки клиенту или возврата 403/429. Этапы 1–5 соответствуют слоям каскада L1–L5; этапы 0, 6, 7 — пред- и пост-обработка (прием, передача в cdn-flow, запись лога). 

### Архитектурный принцип в одном экране

- **Proxy выполняет ВЕСЬ каскад L1–L5** на каждом запросе. Все данные нужные для решений уже подготовлены локально в памяти, никаких сетевых вызовов к backend в hot-path.
- **Antibot-backend** делает только три вещи и никогда не на hot-path: (1) поставляет каталоги на proxy, (2) принимает асинхронный поток логов, (3) фоновый rDNS-воркер для verified-bots.
- Каталоги обновляются на proxy в фоне с двумя SLA задержки:
  - **≤ 30 секунд** для быстрых каталогов: per-resource `policy` (изменение в дашборде клиентом, включая тоггл `attack_mode`), `bot_verification_status` (rDNS-воркер).
  - **≤ 15 минут** для PR-каталогов: `tls_fp_blocklist`, `tls_fp_catalog`, `ua_blacklist`, `ip_blocklist`/`ip_whitelist`, `asn_datacenters`, `tls_fp_browser_profiles` (обновляются продактом через PR).
- Если backend недоступен — proxy продолжает работать с последней успешно загруженной копией (fail-stale), запрос клиента никогда не ждет backend. Конкретный механизм доставки (pull/push/etag/etc.) — на выборе backend-команды.

То есть backend для каскада — это источник конфигурации и приемник логов, а не вычислительный сервис.

**Скоуп — все домены, обслуживаемые edge-пулом.** Каскад работает на всех таких запросах автоматически, отдельного onboarding'а на каждый домен не требуется. Если для домена есть запись в каталоге `policy` — каскад использует ее как override дефолта (mode, Strictness, custom-правила, attack_mode). Если записи нет — применяются системные дефолты пула: `mode=shadow`, `Strictness=Standard`, без custom-правил, `attack_mode=false`. То есть любой новый edge-домен сразу получает observe-only защиту, никакого «не подключенного» состояния внутри edge-пула нет.

Что в скоупе этого документа не разбирается (это отдельные задачи):

- UI дашборда: как клиент видит свою аналитику, как покупает защиту, как настраивает Strictness/правила. Считаем, что клиент уже купил, его политика лежит в нашей базе и доехала до proxy.
- Аналитические виджеты для клиента и для продукта (как именно показываем «X% вашего трафика — боты»).

Что описано здесь:

- **Что лежит на proxy к моменту прихода запроса** — данные, которые уже подготовлены локально, чтобы каскад работал за микросекунды.
- **Путь запроса: от TLS до origin или кеша** — пошагово, основной flow.
- **Что работает в фоне и параллельно** — обслуживающие системы, которые поддерживают эту работоспособность: обновление каталогов, верификация ботов, доставка логов, kill-switch и attack mode.

### Что лежит на proxy к моменту прихода запроса

К моменту, когда TLS-handshake завершен и nginx принял запрос, в локальной памяти worker'а на эдж-нода уже находятся все данные, нужные каскаду:

- **Per-resource policy** для всех клиентских доменов, обслуживаемых этим пулом. Для каждого домена (`Host`): `mode` (shadow / active), Strictness, custom UA-паттерны, ASN-блок клиента, кастомные rate-limit-правила, флаг attack_mode (имеет смысл только при mode=active), IP-whitelist легитимных серверных интеграций (используется на Этапе 2.3 — чтобы серверные интеграции и API-клиенты с известных IP фастпасили до того как дойдут до challenge на L5).
- **Глобальные каталоги:** `tls_fp_blocklist`, `tls_fp_catalog` (известные сигнатуры автоматизации по TLS-fp), `ua_blacklist` (combined regex по UA — системные сигнатуры автоматизации + кураторский bad-bot список), `ip_blocklist`, `ip_whitelist`, `asn_datacenters`, `bot_verification_status` (трехсостоянийный каталог поисковых ботов: `verified` / `rejected` / отсутствует — см. Этап 2.2), `tls_fp_browser_profiles` (ожидаемые cipher_cnt для семейств браузеров).
- **HMAC secret для clearance cookie** — одна строка, общая для всего edge-пула, нужна для подписи cookie на L5 (выдача после challenge, Этап 5.2), проверки cookie на L2 (Этап 2.1) и подписи self-signed nonce challenge-страницы — все без обращения к backend. Доставляется через Puppet (Channel A), грузится на proxy при старте. Ротация:
  - *Плановая* (раз в квартал) — через PR в Puppet-репо + Puppet-run + reload nginx по пулу. Окно несогласованности (одни proxy на новом секрете, другие на старом) — несколько минут; в течение этого окна клиенты с cookie, выданным на одном секрете, могут получить «invalid» на proxy со вторым секретом и перепройти challenge. Это разовая UX-неприятность, продуктово приемлемо.
  - *Экстренная* (компрометация secret'а) — через эскалацию к prod-edge-админам по отдельной incident-процедуре. Это не наш канал и не наш SLA; admin-команда отрабатывает по своему playbook'у. Окно несогласованности то же, но темпы выкатки админ-команда выбирает по серьезности инцидента.
  Ротация инвалидирует все ранее выданные cookie — это by design (часть смысла ротации).

Эти данные обновляются фоновым процессом — см. ниже блок «Что работает в фоне». На сам путь запроса это никак не влияет: все lookup'ы в каскаде идут в локальную память proxy, никаких сетевых вызовов, никаких ожиданий.

### Путь запроса: от TLS до origin или кеша

Принцип каскада прост: каждый следующий слой дороже и/или богаче состоянием, поэтому дешевые проверки идут первыми, чтобы заведомо плохой трафик отсекался максимально рано и не тратил ресурсы на дорогие проверки.

#### Этап 0 — TLS handshake и прием запроса

Клиент устанавливает TLS-соединение с proxy. После handshake данные о нем (версия TLS, список cipher'ов, curves, ALPN, SNI) должны быть доступны каскаду через нативные переменные nginx — `$ssl_protocol`, `$ssl_ciphers`, `$ssl_curves`, `$ssl_alpn_protocol`, `$ssl_server_name`. Именно из них L3 вычисляет TLS-fingerprint; это позволяет считать fp на чистом Lua, без патчей nginx/OpenSSL. Требование к среде — эти переменные должны отдаваться в `access_by_lua` (доступность уточняется с админами). Дальнейшие этапы каскада выполняются для запросов на защищенные клиентские домены.

#### Этап 1 — Hygiene (метод, UA-blacklist)

**Что проверяем:**

- **Метод запроса** — в whitelist (GET, HEAD, POST, OPTIONS по умолчанию). Если запрос идет методом TRACE или PUT — это почти всегда сканер, никаких легитимных причин для таких методов на edge-сайтах нет.
- **User-Agent — в UA-blacklist.** Сопоставление UA-строки с набором паттернов. Один механизм, два источника паттернов, которые сливаются в один каталог `ua_blacklist`:
  1. **Глобальный список** — поддерживается продактом, наполняется через PR в репозиторий по результатам анализа логов. Примеры паттернов: автоматизация (curl, wget, python-requests, scrapy, go-http-client), известные плохие боты (AhrefsBot, SemrushBot, MJ12bot), сканеры уязвимостей (nikto, sqlmap, masscan), скрейперы (ScrapeBot, DataForSeoBot).
  2. **Кастомные паттерны клиента** — клиент через дашборд добавляет свои строки или регулярки для своего ресурса. Хранятся в per-resource policy, применяются поверх глобального списка.
  В дашборде клиента: тоггл «Block known bad bots» включает применение глобального списка к ресурсу + textarea для собственных паттернов.
  Каталог `ua_blacklist` поставляется пустым и наполняется продактом через PR по мере того, как в логах видны паттерны; до наполнения правило никого не блокирует.
- **Header sanity — информационный тег `hygiene:header_anomaly`, не блокирующее правило.** Проверка на комбинации заголовков, которые настоящий браузер не отправляет, а ленивая автоматизация — отправляет. Базовый случай: HTTP/2-запрос без заголовка `Accept` (реальный браузер по HTTP/2 всегда шлет `Accept`). Ловит автоматизацию, которая подделала UA под браузер, но не озаботилась реалистичным набором заголовков — UA-blacklist такую не поймает. Тег не эмитит verdict сам (header-эвристики легко дают false-positive на нестандартных, но легитимных клиентах), а на вердикт не влияет — только копится в `tags` для аналитики (по накопленной статистике потом можно вручную пополнять `ua_blacklist` или правила).

**Откуда данные:** статический конфиг (whitelist методов), каталог `ua_blacklist` (combined regex от backend, глобальный список), каталог `policy` (custom-паттерны клиента), проверка заголовков в Lua (header sanity).

**Стоимость:** наносекунды — set-membership lookup для метода, для UA — одно сравнение по предсобранной combined-регулярке независимо от размера списка.

**Что происходит при срабатывании:** категория blocking → `verdict=block, rule=method_not_allowed | ua_blacklist`. В shadow — только в лог; в active — 403 сразу.

**Безопасное добавление новых UA-паттернов** — через staged rollout (см. раздел «Staged rollout для PR-каталогов» ниже). Новый паттерн сначала добавляется в `staging`, proxy его матчит и пишет факт срабатывания в лог, но не блокирует. После калибровки на реальном трафике паттерн промоутится в `active`.

**Примеры:**

- `TRACE /admin HTTP/1.1` → `verdict=block, rule=method_not_allowed`.
- `User-Agent: AhrefsBot/7.0` → `verdict=block, rule=ua_blacklist`.

#### Этап 2 — Reputation (cookie, verified-bot, IP, ASN, гео)

**Что проверяем по порядку:**

1. **Clearance cookie (HMAC verify)**. Если у клиента в запросе есть `tf_clearance` cookie — он уже когда-то прошел JS challenge и в течение TTL (24 часа в обычном режиме, 1 час если cookie выписан при `attack_mode=on` для этого же домена) считается доверенным. Значения TTL (24ч / 1ч) — системные константы в `defaults.conf`, клиент в дашборде их не настраивает. Выбор между ними делается per-request при выписке cookie на L5 — по состоянию `attack_mode` именно для того хоста, на который пришел запрос. Включение `attack_mode` клиентом A на `example-a.com` не влияет на TTL cookie, выписываемых для других клиентов: cookie скоупится `Domain=example-a.com` и в запросах на чужие хосты вообще не передается. Proxy проверяет HMAC-подпись cookie локально, используя secret из локальной памяти (загружен на старте через Channel A, общий для пула), и сверяет, что cookie предъявляет тот же клиент, которому он был выписан (привязка к идентичности — TLS-fp и подсеть IP: /24 для IPv4, /64 для IPv6). Подпись валидна, привязка совпадает и не истек TTL → клиент считается доверенным браузером: для него пропускаются слои L3 (TLS-fp) и L5 (challenge) — повторно вычислять fp и заново гонять через challenge того, кто его уже прошел, незачем. Но L4 (rate-limits) к нему всё равно применяется: clearance-cookie доказывает «я не JS-неспособный бот», а не «мне можно злоупотреблять» — и прошедший challenge клиент может брутфорсить логин или скрейпить каталог. Если на L4 чисто → `verdict=allow, rule=cookie_valid`; если сработал rate-лимит → выигрывает правило L4 (`verdict=block/challenge, rule=rate`_*). Подпись битая, привязка не совпала или expired → cookie игнорируется, идем дальше по каскаду. Затраты: микросекунды (одна HMAC-операция, никаких сетевых вызовов, никаких lookup'ов в БД).

**Исключение: `attack_mode=on` для этого host'a.** Под атакой L2.1 не доверяет clearance cookie, выданным ДО начала атаки — атакующий мог накопить их заранее, до основной волны. Такие cookie не фастпасят: запрос идет через каскад до L5 (challenge для браузера / соответствующий block для non-browser и unchallengeable). А cookie, выданные уже во время атаки (после перепрохождения challenge, TTL=1ч), фастпасят как обычно — поэтому реальный пользователь проходит challenge один раз за атаку, а не на каждом запросе. Различение «выдан до атаки» vs «выдан во время атаки» — по метаданным самого cookie (время выписки и/или тип TTL); конкретный механизм на стороне реализации. Остальные L2-проверки (verified-bot, IP-whitelist) при `attack_mode=on` работают как обычно — SEO и доверенные серверные интеграции не страдают.
  В отличие от других правил L2, cookie verify — это криптографическая проверка в Lua-коде, а не lookup в каталоге. Поэтому в конфиге секции `[allow]` для нее отдельной регистрации нет — параметры (имя cookie, источник HMAC secret, TTL) задаются как параметры самой Lua-логики. Verdict эмитится напрямую из кода.
   Cookie привязан к домену (домен входит в подпись), поэтому cookie с `site-a.ru` не сработает на `site-b.ru`. При выдаче cookie использовался self-signed nonce с TTL 60с (подписан тем же HMAC secret'ом, что и cookie — любой proxy пула валидирует без shared state); по истечению TTL nonce отвергается, replay невозможен. Подробнее про issue cookie — в Этапе 5.
2. **Verified-bot allowlist (поисковые краулеры).** Поисковых ботов Google, Bing, Yandex, DuckDuckGo нельзя блокировать — упадет индексация. Но их User-Agent легко подделать: любой скрипт может написать «Googlebot» в UA. Поэтому проверка двухступенчатая (PTR + forward DNS), и она вынесена в фоновый rDNS-воркер на backend — DNS на hot-path proxy нет.
  Каталог `bot_verification_status` несет три состояния для IP с поисковым UA:

- `verified` — backend подтвердил через rDNS, что это реальный бот. TTL ~1 час.
- `rejected` — backend проверил и отказал (PTR не сходится, или forward DNS вернул другой IP, или PTR в принципе не вернулся). Это impersonator. TTL ~1 час, симметрично с `verified`.
- **отсутствует** — backend еще не успел проверить (первое появление IP с поисковым UA на нашем пуле, либо TTL прошлой записи истек).
 Логика L2.2 на proxy при UA, претендующем на поискового бота:


| Состояние IP в каталоге                           | Verdict                                   | Что дальше                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------------------------------------------- | ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `verified`                                        | `allow, rule=bot_verified`                | Whitelist-фастпас, остальные слои пропускаются (включая TLS-fp, rate-limits, attack mode).                                                                                                                                                                                                                                                                                                                                                                                                     |
| `rejected`                                        | Никакого fastpath, идем дальше по каскаду | Будет обработан как обычный запрос — скорее всего зацепит `tls_fp_impersonator` или попадет в rate-limits, потом в L5.                                                                                                                                                                                                                                                                                                                                                                         |
| отсутствует *(в каталоге нет записи про этот IP)* | `allow, rule=bot_verified_pending`        | **Provisional whitelist** — пропускаем мягко, чтобы не порушить SEO до того как backend успел проверить. Proxy per-IP state не хранит: pending выдается для каждого запроса с этого IP, пока backend не опубликует verified/rejected в каталог. Бэкенд через приемник логов видит первый pending-запрос, добавляет IP в очередь rDNS-воркера; обычно за секунды-минуты в каталоге появится финальный статус, и все следующие запросы с этого IP уже встретят либо `verified`, либо `rejected`. |


   **Цена provisional fastpath.** Окно «свободного пропуска» — не «ровно один запрос», а «пока rDNS-воркер не опубликует результат». Для impersonator'а, маскирующегося под Googlebot с нового IP, это означает: он успеет пройти несколько запросов до того, как попадет в `rejected`. После этого — `rejected` (TTL 1ч), и дальше будет ловиться нормально. Для распределенной атаки с массовой ротацией IP это не страшно: per-domain rate-limits на L4 ловят такой паттерн, а одиночные «свободные» запросы — шум на уровне фона. Цена приемлемая ради гарантии, что любой настоящий новый Googlebot-IP не получит challenge до того как мы его проверили.
   **На proxy — простой lookup в локальной памяти (наносекунды), DNS на hot-path нет.**
3. **IP whitelist** — два источника, проверяются вместе:

- **Системные** — IP-адреса нашего мониторинга, чек-сервисов, доверенные системные клиенты (общий каталог `ip_whitelist`).
- **Per-resource** — IP-адреса легитимных серверных интеграций клиента, которые он заранее зарегистрировал в дашборде (часть per-resource `policy`). Это основной способ для API-клиентов, server-to-server интеграций и бэкенд-крон-задач избежать challenge на L5.
 Срабатывание любого источника — категория allow → `verdict=allow, rule=ip_whitelist`. В active — фастпас, остальные слои пропускаются; в shadow — только лог, каскад идет дальше.

1. **IP blocklist** — IP, которые мы уже знаем как плохие (попали по результатам анализа логов или жалоб). Категория blocking → `verdict=block, rule=ip_blocklist`.
2. **ASN-блокировка клиента.** ASN (Autonomous System Number) — номер автономной системы, которой принадлежит IP-адрес. Каждый крупный хостинг-провайдер, облако или VPN имеет свой ASN. *Практический сценарий:* атака идет с IP разных стран, но все они принадлежат одному облаку (AWS, DigitalOcean, Hetzner) или VPN-сервису — один ASN-номер закрывает всю подсеть провайдера одним правилом. Клиент вводит ASN-номера в дашборде, они попадают в per-resource policy. При совпадении — категория blocking → `verdict=block, rule=asn_customer`.
3. **Гео.** Если у ресурса задан whitelist стран и страна запроса в него не входит — категория blocking → `verdict=block, rule=geo_blocklist`.

**Информационные теги L2** (не правила, не приводят к verdict, нужны для аналитики):

- `reputation:asn_dc` — IP из ASN крупного публичного датацентра (Hetzner, OVH, DigitalOcean, AWS, GCP, Azure). Сам по себе тег ничего не блокирует и не триггерит challenge — потому что из ДЦ может ходить и легитимный API-клиент. Используется для аналитики («% нашего трафика из ДЦ»). На вердикт не влияет; сочетание с другими сигналами в логах помогает интерпретации (DC IP вместе со сработавшим `tls_fp_impersonator` — явный indicator маскировки под Chrome), но это анализ, не рантайм-решение.

Источник данных для тега — каталог `asn_datacenters`.

**Откуда данные:** статические списки в конфиге (системные ASN-датацентры) + MaxMind GeoIP/ASN базы (уже есть на prod-edge-proxy) + per-resource customizations через каталог `policy` (custom ASN-блок клиента, custom geo-whitelist).

**Стоимость:** микросекунды — CIDR-matching и hash-lookup.

#### Этап 3 — TLS-fingerprint

**Что проверяем:** уникальную сигнатуру клиента, вычисленную из его TLS handshake. Она определяется реальным TLS-стеком (Chrome NSS, Firefox NSS, OpenSSL, Go crypto/tls, python ssl) и не меняется при подмене User-Agent.

**Как вычисляется:** на основе тех самых `$ssl`_* переменных, которые nginx заполнил после handshake:

```
fp = L<ver><sni_flag><cipher_cnt><alpn>_<hash_b>_<hash_c>
```

Fingerprint — это короткая строка из двух частей: человекочитаемого префикса и двух хэшей. Префикс собирается из параметров handshake и читается «на глаз»:


| Часть          | Что значит                                                             | Пример |
| -------------- | ---------------------------------------------------------------------- | ------ |
| `L`            | фиксированный префикс нашего формата                                   | `L`    |
| `<ver>`        | версия TLS: `12` = TLS 1.2, `13` = TLS 1.3                             | `13`   |
| `<sni_flag>`   | прислал ли клиент SNI: `d` — да, `i` — нет                             | `d`    |
| `<cipher_cnt>` | сколько cipher'ов предложил клиент (после очистки от GREASE, см. ниже) | `15`   |
| `<alpn>`       | согласованный протокол: `h2` или `h1`                                  | `h2`   |


Дальше через `_` идут два хэша — они сжимают точные списки в компактный вид (берём SHA-256 и оставляем первые 12 hex-символов):

- `hash_b` — хэш от **отсортированного списка cipher'ов** (после очистки от GREASE). Отвечает на «какой именно набор шифров предложил клиент».
- `hash_c` — хэш от **списка curves + ALPN + версии TLS**. Дополнительный различитель по другим параметрам handshake.

Пример итогового fp для реального Chrome: `L13d15h2_1ed0482b9b4c_b50336ab2a86`.

**Про очистку от GREASE (RFC 8701).** GREASE — это случайные «пустышки», которые браузеры (Chrome, Safari) подмешивают в список cipher'ов и curves на каждом подключении специально, чтобы значения менялись. Если их не вырезать перед хэшированием, fp одного и того же браузера будет разным при каждом запросе, и каталог сигнатур станет бессмысленным. Поэтому очистка от GREASE обязательна — после неё fp стабилен и одинаков для одного TLS-стека.

Полученный fp кэшируется локально на proxy на 60 секунд, чтобы повторные запросы того же клиента не пересчитывали хэш.

**Проверки на основе fp:**

1. **fp клиента есть в каталоге `tls_fp_blocklist`** (категория blocking) → `verdict=block, rule=tls_fp_blocklist`. Туда попадают fp, которые мы уже знаем как боты, по результатам анализа аналитики.
2. **UA-family ↔ fp mismatch.** В каталоге `tls_fp_catalog` указано, какие cipher-hash соответствуют каким известным семействам автоматизации (python-requests, curl, Go, okhttp). Если в UA «Chrome», а fp совпадает с hash python-requests — это impersonator. Категория soft → `verdict=challenge, rule=tls_fp_impersonator`.
3. **Cipher count выпадает из browser-profile.** В каталоге `tls_fp_browser_profiles` хранятся ожидаемые `cipher_cnt` для семейств браузеров (Chrome: 15, Firefox: 16, Safari: 20). Если UA похож на Chrome, но cipher_cnt=11 — это подозрительно. Категория soft → `verdict=challenge, rule=tls_fp_suspicious_ciphers`.
4. **Браузерный fp из датацентра.** fp выглядит как браузер (семейство по cipher-профилю), но IP относится к датацентровому ASN (`asn_datacenters`) — аномалия: настоящие пользователи не ходят из публичного ДЦ. Категория soft → `verdict=challenge, rule=tls_fp_dc_browser`. Срабатывает после allow-фастпасов L2, поэтому verified-bot и зарегистрированные клиентом IP-whitelist (легитимные облачные интеграции, S2S) его не задевают. Детект headless-движка внутри настоящего браузера и поведенческий анализ сессий — post-MVP (L6, см. сравнение с Cloudflare).

**Информационные теги L3** (не правила, не приводят к verdict, нужны для аналитики):

- `tls_fp:automation_ua` — в UA явные признаки автоматизации;
- `tls_fp:no_sni` — клиент пришел без SNI.

Все теги (со всех слоев) попадают в одно поле лога `tags` с namespace-префиксом — см. JSON-схему в Этапе 8.

**Стоимость:** доли микросекунды — один sha256 на ~50 байт + два sorted-membership lookup'а.

#### Этап 4 — Rate-limits (поведенческие)

**Где мы в каскаде.** Все предыдущие слои (L1–L3 плюс пассивные allow-правила на L2) — это identity-проверки: они отвечают на вопрос «кто этот клиент» (UA, IP, ASN, гео, TLS-fp, есть ли cookie/whitelist). Статические сравнения одного запроса с известными нам списками и сигнатурами. L4 закрывает ортогональный класс сигналов — поведение во времени: сколько запросов клиент делает, по каким путям, с какой регулярностью. Это уже не «кто», а «что он делает». Идентичность может быть кристально чистая (легитимный Chrome из residential-IP с правильным TLS-fp), а клиент при этом брутфорсит `/login` или скрейпит каталог — поймает его только L4. Без этого слоя каскад пропускает целый класс атак, где identity-сигналы недостаточны.

**Что проверяем:** скользящие счетчики по различным ключам, GCRA-style (generic cell rate algorithm — компактная sliding-window реализация без хранения timestamp'ов всех запросов). На каждом профиле параллельно работают два окна — короткое (10 с) и длинное (1 мин); правило срабатывает, если любое из них превышено. Зачем два: короткое ловит burst (бот делает 500 req за 5 секунд и уходит), длинное ловит «медленных» скрейперов, которые держатся чуть ниже burst-порога часами. Выбор GCRA продиктован стоимостью: одна 64-битная ячейка состояния на ключ, обновление за одну арифметическую операцию — критично при сотнях тысяч уникальных ключей на эдж-нода.

##### Системные профили (применяются всегда)


| Профиль            | Ключ счетчика            | 10 с | 1 мин | Категория | Что ловит                                  |
| ------------------ | ------------------------ | ---- | ----- | --------- | ------------------------------------------ |
| **rate_ip**        | IP                       | 100  | 600   | blocking  | Общий лимит на IP                          |
| **rate_ip_ua**     | IP+UA                    | 100  | 600   | blocking  | Один клиент через несколько UA-вариантов   |
| **rate_api**       | IP (только на API-путях) | 50   | 300   | blocking  | Перегрузка API                             |
| **rate_tls_fp**    | TLS-fp                   | 50   | 300   | blocking  | Бот ротирует IP, но TLS-стек один и тот же |
| **rate_scan_urls** | IP (уникальные URL)      | 50   | 200   | blocking  | Скрейпинг — много разных URL с одного IP   |


**Graceful degradation для `rate_tls_fp`.** Если по какой-то причине TLS-fp не вычислился на Этапе 3 (handshake без SNI, нестандартный TLS-клиент, ошибка вычисления) — правило `rate_tls_fp` просто не применяется к этому запросу. Остальные rate-rules (rate_ip, rate_ip_ua, rate_api, rate_scan_urls) продолжают работать. То есть отсутствие fp не приводит к ошибке каскада, просто этот конкретный ключ счетчика не используется.

##### Клиентские правила per-path (применяются поверх)

Клиент в дашборде задает свои правила: на каких путях, с каким лимитом, что делать при превышении. Каждое правило — это:

- **path** — паттерн (`/login*`, `/api/*`, `/search`)
- **methods** — HTTP-методы (опционально)
- **rps** — средняя скорость запросов в секунду с одного IP
- **burst** — допустимый кратковременный всплеск
- **action** — `block` | `challenge` | `log_only`

**Порядок применения на L4: сначала клиентские правила, потом системные.** Клиентские rate-rules для этого хоста проверяются первыми, по порядку в списке клиента; первое совпадение выигрывает (его action — `block`/`challenge`/`log_only` — становится результатом L4 для этого запроса, системные правила дальше не запускаются). Если ни одно клиентское правило не сматчилось (по path/method/key) — запускаются системные профили в порядке `rate_ip → rate_ip_ua → rate_api → rate_tls_fp → rate_scan_urls`, первое превышение выигрывает. Логика: клиент в своем дашборде знает специфику своего домена точнее, чем системные эвристики, и явная настройка должна перевешивать дефолт.

Чтобы клиенту не настраивать с нуля, в дашборде есть presets (фича UI-слоя, не отдельная сущность каскада). Preset — это шаблон, который при выборе раскрывается в обычную запись `policy[host].rate_rules`. На proxy preset как объект не приезжает; туда уходит готовое правило. Каталог пресетов хранится во frontend / backend dashboard (что удобнее команде), на proxy не доставляется:


| Preset                  | Путь по умолчанию | RPS | Burst | Action    | Задача                         |
| ----------------------- | ----------------- | --- | ----- | --------- | ------------------------------ |
| Login Protection        | `/login*`         | 5   | 10    | challenge | Защита от брутфорса            |
| Registration Protection | `/register*`      | 3   | 5     | block     | Защита от массовой регистрации |
| API Protection          | `/api/*`          | 20  | 40    | block     | Лимит на API                   |
| Search Protection       | `/search*`        | 10  | 20    | challenge | Защита от скрейпинга           |
| General Limit           | `/`               | 50  | 100   | log_only  | Общий лимит на весь трафик     |


Клиент применяет preset → меняет путь под структуру своего сайта (`/login` → `/account/sign-in`) → готово.

##### Что делает каждый `action` при превышении

- `block` — категория blocking → `verdict=block, rule=rate_*`. В active отдается 429 Too Many Requests с `Retry-After`. Каскад заканчивается, до L5 запрос не доходит.
- `challenge` — категория soft → запрос помечается «нужна верификация».
- `log_only` — только запись в лог, никакого влияния на дальнейшие этапы.

##### Где живут счетчики

Локально в памяти каждого proxy, per-proxy worker. Это сознательный компромисс v1: при распределении трафика между несколькими proxy суммарный допустимый RPS пропорционально выше (каждый proxy видит только свою долю трафика и считает только ее). Глобально точный rate limit потребует shared storage между proxy — это v2.

**Стоимость:** микросекунды — sliding window counter increment + сравнение с порогом.

#### Этап 5 — Verification (active)

**Где мы в каскаде.** Это финальный слой каскада: запрос прошел все identity-проверки (L1–L3, плюс пассивные allow-правила на L2) и behavior-проверки (L4). Сюда доходит, только если ничего его не отбило сразу как `block` и ничего не дало `allow`-фастпас. По пути могли накопиться challenge-flags — от soft-категории правил:

- `tls_fp_impersonator`, `tls_fp_suspicious_ciphers`, `tls_fp_dc_browser` (Этап 3) — soft
- L4 client rules с `action=challenge` (Этап 4) — soft

L5 — это исполнитель: единая точка, где смотрят на накопленные challenge-flags + attack_mode + Strictness, и решают что выдать клиенту. Никакие предыдущие слои сами challenge не выдают — они только выставляют флаги.

Пассивные allow-правила (clearance cookie, verified-bot, IP-whitelist) живут раньше, на L2 (Этапы 2.1–2.3) — клиенты с валидным cookie, подтвержденные краулеры и зарегистрированные серверные IP сюда вообще не доходят, потому что L2 уже выдал им `verdict=allow`.

**Где L5 исполняется физически.** Полностью на proxy, без обращения к backend. Весь жизненный цикл challenge — выдача HTML-страницы, генерация nonce, проверка ответа клиента, подпись cookie HMAC'ом — работает локально, на тех же примитивах, что и cookie verify на Этапе 2.1: HMAC secret из локальной памяти proxy. Backend в hot-path не вмешивается. Единственное, что уходит асинхронно в backend — это лог с challenge-pass-событием с собранным browser fingerprint (для аналитики).

**Что будет проверяться (по порядку):**

##### 5.1. Решение про верификацию

Решение, нужна ли активная верификация сейчас, принимает `should_challenge()`. Это вычисляемая на L5 функция: L5 считает ее на каждый запрос из трех входов:

1. **Тоггл `attack_mode`** для этого хоста (per-host). Если включен — каждый запрос, дошедший до L5, требует верификации независимо от всех остальных сигналов. См. ниже про Under Attack mode.
2. **Накопленные challenge-flags** с предыдущих слоев (tls_fp_impersonator / tls_fp_suspicious_ciphers / tls_fp_dc_browser с L3, rate-rules с action=challenge с L4). Запрос дошел до L5 → значит хотя бы один flag уже сработал.
3. Что делать дальше — определяет тоггл Strictness в дашборде, бинарный:


| Strictness                                        | Что делает L5 при накопленных challenge-flags                                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Standard** *(дефолт для всех новых клиентов)*   | Любой системный challenge-flag (`tls_fp_impersonator`, `tls_fp_suspicious_ciphers`, `tls_fp_dc_browser`, L4 rate-rules с action=challenge) → выдаем challenge. Стандартное поведение для сайтов без специфики.                                                                                                                                                                                                                                                                 |
| **Permissive** *(включается клиентом в дашборде)* | Системные challenge-flags не триггерят challenge — клиент через L5 проходит, физически запрос идет дальше в prod-edge-flow. В лог пишется `verdict=permissive, rule=<имя последнего soft-флага>` — отдельный verdict нужен, чтобы в аналитике сразу было видно «здесь сработало бы на Standard, но Permissive подавил». Профиль для доменов, где легитимный не-браузерный трафик не поддается точечному перечислению (см. ниже «Зачем Permissive существует»). |


**Дефолт для каждого нового домена — `Strictness=Standard`.** Это значит, что сразу после подключения к Bot & Abuse Controls клиент работает на стандартных порогах верификации. Чтобы переключить в Permissive — явное действие в дашборде.

**Важное исключение из обоих режимов: клиентские rate-rules с `action=challenge` всегда уважаются.** Если клиент сам в дашборде сконфигурировал «Login Protection: 5 RPS, challenge» — challenge выдается при превышении даже в Permissive. Тоггл Strictness влияет только на системные soft-signals (рассчитываемые антиботом эвристики), не на явные настройки клиента.

**Permissive — это не «выключенная защита».** Блокирующие правила (ua_blacklist, ip_blocklist, asn_customer, geo_blocklist, tls_fp_blocklist, системные rate-rules с action=block, rate_ip и др.) продолжают блокировать как обычно — Strictness влияет только на верификацию soft-flags. В случае, если клиент вообще не хочет реальных блокировок (например, для тестирования) — он переключает `mode=active → shadow` (тогда каскад только наблюдает).

**Зачем Permissive существует.**

Strictness — доменный тоггл (в Bot & Abuse Controls подключение идет на уровне домена второго уровня; поддомены отдельно не заводятся). Он влияет на весь трафик клиента.

Точечные кейсы — известные API-партнеры, конкретные webhook-источники, отдельные пути — уже решаются другими механиками каскада:

- IP/ASN известных интеграций → `whitelist_ip` или per-resource IP-whitelist → L2 фастпасит их до того, как Strictness вообще применится;
- Per-path лимиты и блокировки → клиентские rate-rules L4 и blocking-правила L1 с path-matcher'ом;
- Боты с rDNS (Googlebot, Bingbot и т.п.) → `bot_verification_status` → L2 фастпасит автоматически.

**Permissive клиенту нужен, когда таких точечных правил недостаточно:** легитимных не-браузерных источников много, заранее они не известны, перечислять их whitelist'ом нереалистично. Типичные ситуации:

- **Превью-боты соцсетей и мессенджеров** (Telegram, Slack, Discord, FB, LinkedIn, Twitter), RSS-агрегаторы, аптайм-мониторинги — массовые, разнородные, многие не в `bot_verified_ips`, IP-диапазоны меняются. Для медиа и контент-площадок терять их = терять превью в чатах.
- **B2B-домен с разнообразными серверными клиентами** — десятки партнерских интеграций со своих ASN/IP, без браузерного UA, поименно whitelist'ить дорого и не масштабируется.
- **Калибровочный период после онбординга** — клиент сначала смотрит в логах, какие системные soft-flags часто срабатывают на его реальном трафике, потом переключает на Standard (плюс точечные whitelist'ы там, где они нужны).

**Когда Permissive НЕ оправдан** (несмотря на смешанный трафик):

- Браузерная часть домена несет основную выручку (e-commerce checkout, оплата, личный кабинет) — потеря даже доли процента реальных пользователей хуже, чем пропущенные боты. Лучше Standard + точечные whitelist'ы для API-партнеров.
- Под активной атакой используется `attack_mode=on`. Важно: Permissive под атакой просто не действует (не ослабляет защиту).

##### 5.2. Выбор и выдача верификации

Если `should_challenge()=true`, мы НЕ всегда выдаем JS challenge. Не весь легитимный трафик идет из браузера — API-клиенты, мобильные приложения, server-to-server интеграции, IoT не выполняют JS. Если выдать им JS challenge — мы заблокируем легитимные не-браузерные запросы клиента.

Поэтому при `should_challenge()=true` каскад выбирает механизм верификации по типу клиента:

**Ветка A: клиент похож на браузер** (UA содержит Mozilla/Chrome/Safari/Firefox/Edge и при этом проходит базовые header-проверки) → JS challenge:

- Браузеру показывается промежуточная страница «Проверяем соединение…». HTML+JS-шаблон этой страницы доставляется на proxy как часть Lua-кода каскада через Channel A (Puppet); версия JS всегда совпадает с версией каскада, который ее сервит. Proxy подставляет в шаблон self-signed nonce — токен, подписанный тем же HMAC-secret'ом, что и clearance cookie, с зашитыми внутрь `timestamp`, `domain`, `expiry` (TTL 60с). Поскольку секрет одинаков на всех proxy пула, проверить такой nonce может любой proxy — клиент может получить challenge на proxy A, ответить через proxy B, все валидируется без shared state и без обращения к backend. Replay-защита — через `expiry`: если nonce старше 60с, proxy отвергает.
- На странице выполняется JavaScript-задача:
  - **Доказательство исполнения** — браузер решает вычислительную задачу над выданным сервером одноразовым токеном (nonce). Реальный браузер делает это незаметно за доли секунды; бот, который страницу не исполняет, не решит ее, а массовая ферма платит ощутимую цену за каждый запрос — поэтому дешевый перебор не окупается. Сам эндпоинт проверки защищен от злоупотребления: nonce сгорает при первой же попытке проверки — успешной или нет (при сбое клиент берет новый), а `/__challenge/verify` под rate-limit — так что один добытый nonce нельзя превратить в поток проверок и нагрузить им proxy.
  - **Опциональный checkbox** «Подтвердите, что вы человек» — показывается при высоком подозрении.
  - **Browser fingerprint** — при прохождении собираются характеристики клиента (UA, экран, Canvas, WebGL, timezone, язык). Они проверяются на непротиворечивость по высокоуверенным сигналам: challenge заваливает только грубое противоречие (например, UA Chrome поверх TLS-fp семейства python-requests), а рандомизированные или скрытые приватными браузерами и расширениями значения (Canvas/WebGL и подобные) допускаются — чтобы не штрафовать privacy-conscious пользователей. Тот же fingerprint уезжает с challenge-pass-событием в телеметрию (event_type=`challenge_pass`, по тому же пути, что и обычные логи) для долгосрочной аналитики — распределение легитимных fingerprint'ов, выявление паттернов headless-инструментов и датасет под будущие ML-модели L6.
- После успешного прохождения браузер получает clearance cookie (подписан HMAC, см. Этап 2.1) и редиректится на запрошенный URL. Пропуск привязан к тому клиенту, который его заработал: передать или переиспользовать его на другом клиенте нельзя.
**Атрибуты cookie `tf_clearance`:**
  - `HttpOnly=true` — JS на странице клиента не читает cookie (защита от кражи через XSS).
  - `Secure=true` — отправляется только по HTTPS (наш edge-пул в любом случае HTTPS-only).
  - `SameSite=Lax` — отправляется при top-level навигации на этот домен, не на cross-site субзапросах. Достаточно для фастпаса обычных переходов, не утекает на чужие сайты.
  - `Path=/` — действует на весь домен.
  - `Domain=<host>` — строго на этот хост, без leading dot. Cookie с `example-a.com` не работает на `example-b.com` и не работает на поддоменах `*.example-a.com`. Каждый защищаемый хост — свой независимый пропуск.
- **Что видит реальный пользователь:** страница с анимацией, исчезает через 1–2 секунды; больше в течение 24 часов ее не увидит.
- **Что видит бот, маскирующийся под браузер:** HTTP 303 → страница с задачей. Не исполняет ее — не проходит. Подделывает характеристики браузера — не сходится проверка. Решает задачу массово — платит за каждый запрос и не может разнести один заработанный пропуск на свою ферму.

**Ветка B: клиент явно не браузер** (UA содержит curl/python-requests/Go-http-client/мобильное-SDK/etc., или нет стандартных browser-заголовков) → JS challenge выдавать бессмысленно, он его не пройдет по дизайну. И «представиться» ему уже нечем: все механизмы доверенности (clearance cookie, IP-whitelist) уже проверены на L2, и ни один не сработал — иначе запрос сюда не дошел бы.

Поэтому → категория blocking → `verdict=block, rule=non_browser_blocked`. Блокируем как подозрительного.

**Когда Ветка B срабатывает.** Только если `should_challenge()=true` на Этапе 5.1 — то есть либо включен `attack_mode`, либо клиент в Standard-режиме Strictness и накопил системные challenge-flags. В Permissive-режиме Branch B не срабатывает: в Permissive `should_challenge()` для системных flags возвращает false, до Branch B запрос вообще не доходит, физически идет дальше через каскад. В лог при этом пишется `verdict=permissive, rule=<имя последнего soft-флага>` — это и есть смысл Permissive (не мешать non-browser клиентам без явной необходимости), а отдельный verdict позволяет в аналитике видеть «здесь Standard заблокировал бы».

**False-positive recovery loop.** Заблокированный запрос попадает в лог со всеми деталями (IP, UA, какие challenge-flags сработали, какие именно правила его до L5 довели, fingerprint). Клиент в дашборде видит этот блок в виджете «Заблокированные запросы» и может:

- Одним кликом добавить IP в per-resource IP-whitelist (Этап 2.3) — если уверен что эти серверные интеграции легитимны;
- Оставить как есть — продолжать блокировать.

**Как изменение доезжает до proxy.** Per-resource IP-whitelist — часть per-resource `policy` (быстрый каталог). Поток: клик в дашборде → API backend → запись в БД → обновление каталога `policy` → доставка на все proxy edge-* пула. Продуктовый SLA — ≤ 30 секунд с момента клика до того, как любой proxy пула начнет фастпасить этот IP на L2.3. Все запросы от этого IP, прилетевшие в окне доставки, обрабатываются по старому состоянию (продолжают блокироваться); после применения — фастпас. Удалить запись из whitelist (если ошиблись) — обратная редакторская операция в том же интерфейсе дашборда: клик «удалить» → API backend → запись пропадает из БД → каталог `policy` пересобирается → доставка на proxy. SLA тот же: ≤ 30 секунд с момента клика до того, как все proxy пула перестанут фастпасить этот IP. Отдельного undo-механизма нет.

После применения следующий запрос от этого клиента сразу проходит фастпасом на L2.3, не доходит до L5. Это основной механизм работы с false-positive в Ветке B.

**Ветка C: Запрос протокольно не подходит под challenge.** JS challenge работает только для GET-запросов от браузера, ожидающего HTML: proxy отдает HTML-страницу с JS, браузер выполняет токен, получает cookie и делает новый GET на тот же URL. Эта механика ломается, если:


| Признак запроса                                                                                    | Почему JS challenge не сработает                                                                                                                                                                                                                                                                                                |
| -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Метод не GET (POST/PUT/PATCH/DELETE)                                                               | После прохождения challenge JS делает `window.location = <original_url>` — это GET. Тело исходного POST/PUT нигде не сохраняется (редирект 303 сбрасывает body; 307 ломает challenge-страницу). Реализовать «сохранить body и переотправить» можно только клиентским SDK с XHR/fetch-перехватчиком — у нас его нет.             |
| `Upgrade: websocket` (WebSocket-handshake)                                                         | Клиент ждет `101 Switching Protocols`. HTML-ответ ломает upgrade — соединение не установится.                                                                                                                                                                                                                                   |
| `Accept` явно не включает `text/html` (например `application/json`, `application/grpc`, `image/`*) | Клиент не браузер, HTML-страницу не отрендерит, JS не выполнит. Получит HTML вместо ожидаемого JSON/binary и сломается на парсинге. Дефолт при отсутствии `Accept` header'a — трактовать как `*/`* (не html) → unchallengeable. (Продуктовая команда может скорректировать в реализации, если найдут практический контр-пример) |


Решение Ветки C при `should_challenge()=true`: `verdict=block, rule=unchallengeable_request`. Recovery loop тот же что у Ветки B — клиент видит блок в дашборде, может добавить IP в per-resource IP-whitelist.

**Зачем отдельное правило `unchallengeable_request`, а не общий `non_browser_blocked`.** Клиенту в дашборде полезно отличать две разные причины блокировки:

- `non_browser_blocked` — UA не похож на браузер (curl/python/SDK). Лечится whitelist'ом по IP/ASN известных серверных интеграций.
- `unchallengeable_request` — UA, возможно, и браузерный, но запрос протокольно не challenge'абелен (POST из браузера, WebSocket из браузера). Лечится либо whitelist'ом источника, либо переходом домена в Permissive (если таких запросов много и они легитимны).

**В v1 это все.** Полноценные альтернативные механизмы верификации для не-браузерного трафика (mTLS, OAuth-проверка, мобильный SDK с подписанным attestation-токеном) — это не в v1.

**Рекомендация клиенту с API-heavy сайтом:** заранее зарегистрировать в дашборде IP-диапазоны легитимных серверных интеграций — они сработают на Этапе 2.3 и до L5 не дойдут. Если IP интеграции не было заранее добавлено — увидите блок в дашборде и сможете разблокировать постфактум (см. recovery loop выше).

##### 5.3. Under Attack mode

Форсированный режим, переключаемый тоггл `attack_mode` per-host (свой тоггл на каждый защищаемый домен). Глобального тоггла «attack_mode на весь пул» нет.

При `attack_mode=on` для домена:

- **Каждый запрос, дошедший до L5, форсится на верификацию** независимо от Strictness и накопленных flags. На L5 разводка по веткам сохраняется: браузер → JS challenge (Ветка A); non-browser → `verdict=block, rule=non_browser_blocked` (Ветка B); протокольно несовместимый запрос → `verdict=block, rule=unchallengeable_request` (Ветка C). То есть attack_mode не отменяет защитные блокировки L5, а форсит `should_challenge()=true` для всех.
- **Cookie verify на L2.1: cookie, выданные до начала атаки, не фастпасят** — атакующий мог накопить их заранее на свежевыданных IP, мы им не доверяем. Реальные пользователи перепроходят challenge один раз и получают свежий cookie с TTL=1ч, который фастпасит до конца атаки (см. ниже).
- **Verified search bots (Этап 2.2) и IP-whitelist (Этап 2.3) продолжают фастпасить** — SEO и явно доверенные клиентом серверные интеграции не страдают.
- Rate-лимиты на L4 применяются как обычно ко всему, что дошло до L4 — в том числе к держателям clearance-cookie (cookie пропускает L3 и L5, но не L4, см. L2.1). Полный обход L4 — только у verified-bot и IP-whitelist.
- **Clearance TTL для новых cookie снижается до 1 часа** (вместо обычных 24) на время `attack_mode=on`. Старые 24-часовые cookie не инвалидируются физически, но при `attack_mode=on` все равно не работают (см. выше); после выключения attack_mode они снова начинают фастпасить до своего expiry.

**Когда включать:**

- Идет DDoS или bot-атака на этот домен
- Резкий рост нагрузки на origin клиента
- Превентивно перед ожидаемым вирусным трафиком на домене (запуск, публикация, PR-акция)

**Где живет:** тоггл `attack_mode` для конкретного `host` в каталоге `policy` → proxy через Channel C (≤ 30 секунд до распространения).

**Стоимость L5 в целом:** issue challenge — секунды на клиенте (выполнение JS). На proxy — выдача страницы и подпись cookie через HMAC, микросекунды.

#### Этап 6 — Передача запроса в стандартный CDN-flow

Если каскад дошел сюда без блокирующего срабатывания — запрос уходит дальше по обычному CDN-flow (cache lookup, origin fetch, доставка ответа). 

К origin не добавляются никакие новые заголовки от антибота: origin клиента не должен видеть и зависеть от того, что перед ним что-то проверили. В ответе клиенту тоже нет антибот-заголовков — пользователь не должен видеть «следов» каскада.

**Важное свойство порядка этапов:** антибот применяется до того, как запрос попадает в cdn-flow (в т.ч. до cache lookup). Поэтому даже cached responses защищены от мусорных запросов — если бот пришел за «легкой» закешированной картинкой и каскад его не пустил, cdn этот запрос не увидит. Bot & Abuse Controls защищает не только origin клиента (от нагрузки), но и наш собственный кеш-слой.

#### Этап 7 — Запись лога

После доставки ответа proxy собирает одну структурированную JSON-запись с финальным вердиктом и всеми сигналами, которые сработали по пути:

```json
{
  "request_id": "...",
  "timestamp": "2026-05-18T14:30:00.123Z",   // ISO 8601 с миллисекундами
  "edge_id": "edge-042",                // идентификатор proxy-узла, обработавшего запрос (для агрегации)
  "resource_id": "...", "host": "...", "path": "...",
  "method": "...", "status": ..., "latency_ms": ...,
  "ip": "...", "asn": "...", "geo_country": "...",
  "ua": "...",
  "tls_fp": "L13d15h2_1ed0482b9b4c_b50336ab2a86",
  "tls_cipher_count": 15, "tls_alpn": "h2", "tls_sni_present": true,
  "tags": ["reputation:asn_dc"],  // объединенный массив тегов со всех слоев с namespace-префиксом
  "flags": ["tls_fp_impersonator"],  // все накопленные по пути challenge-флаги (soft-правила, что сработали). Пустой если флагов не было
  "stage": "rate_limits",       // на каком этапе финальное правило сработало
  "verdict": "block",           // pass | block | challenge | allow | permissive
  "rule": "rate_ip",            // код ФИНАЛЬНОГО (терминального) правила, пусто при pass
  "action": "block",            // что должно было произойти: block | challenge | allow | log_only | pass
  "mode": "shadow",             // mode ресурса на момент запроса: shadow | active
  "staging_match": []           // массив staging-паттернов, сработавших на запросе (но не повлиявших на verdict). Пустой если ничего не матчилось
}
```

**Финальный `verdict` и `rule` — это терминальное решение, ровно одно на запрос.** Поле `rule` содержит код **последнего (терминального)** сработавшего правила. При `verdict=pass` оно пустое; при `verdict=permissive` — имя последнего soft-флага, который был бы триггером challenge на Standard.

**Но всё, что сработало по пути, не теряется — оно в массивах.** Каскад короткозамыкается только на терминальном (блокирующем/allow) правиле; до этого soft-флаги и теги накапливаются и логируются целиком:

- `flags` — все накопленные challenge-флаги (soft-правила: `tls_fp_impersonator`, `tls_fp_suspicious_ciphers`, `tls_fp_dc_browser`, клиентские rate-rule с `action=challenge`).
- `tags` — все сработавшие информационные теги.

Пример: сработали `tls_fp_impersonator` (soft) на L3 и затем `rate_ip` (blocking) на L4. В логе: `verdict=block, rule=rate_ip` (терминальное), `flags=["tls_fp_impersonator"]` (накопленный флаг сохранён для аналитики). Логировать правила, которые не выполнились из-за короткого замыкания (например, L5 после блока на L4), нельзя — они физически не отработали.

Запись отправляется с proxy на antibot-backend асинхронно, запросы клиентов на этом не блокируются. Детали доставки лога с proxy до приемника телеметрии — в блоке «Что работает в фоне» ниже.

#### Что происходит, если каскад дал `verdict=block` или `verdict=challenge`

Поток обрывается на соответствующем этапе каскада — до cache lookup, до origin, до доставки нормального ответа. Дальше:

- `verdict=block` → клиенту возвращается 403 (для rate-лимитов — 429 с заголовком `Retry-After`). Cache не трогаем. Origin не нагружаем. Запись лога с `verdict=block` все равно пишется.
- `verdict=challenge` → клиенту возвращается HTML-страница JS challenge. Если клиент проходит JS-задачу — он получает clearance cookie и делает запрос заново, на этот раз cookie фастпасит его на этапе 2.1 и каскад идет до конца. Если не проходит — застревает на странице challenge.

### Что работает в фоне и параллельно

Чтобы основной flow в предыдущей секции работал быстро и надежно, его обслуживает три типа фоновых систем.

#### Постоянные фоновые процессы (работают все время сами)

**Обновление каталогов на proxy.** Backend и proxy постоянно синхронизируют каталоги в фоне. Продуктовый контракт:

- **Быстрые каталоги** (`policy`, `bot_verification_status`) — изменение применяется на пуле proxy с задержкой не более 30 секунд.
- **PR-каталоги** (`tls_fp_blocklist`, `tls_fp_catalog`, `ua_blacklist`, `ip_blocklist`/`ip_whitelist`, `asn_datacenters`, `tls_fp_browser_profiles`) — изменение применяется на пуле proxy с задержкой не более 15 минут от merge'а PR.
- Подмена данных на proxy атомарна, без блокировок и без потери трафика.
- При недоступности бэкенда proxy продолжает работать с последней успешно загруженной копией каталогов сколько угодно долго (fail-stale). Запрос клиента никогда не ждет обновления каталогов.
- Метрика «как давно proxy не получал свежих каталогов» алертит при превышении SLA.

Конкретный механизм синхронизации (pull-таймер с proxy, push с backend, server-sent events, любой другой) — на выборе команды, продуктовое требование только в вышеуказанных пунктах.

**Reverse-DNS воркер для verified bots.** Фоновая горутина на antibot-backend проверяет IP, которые в логах фигурировали с UA содержащим `Googlebot/bingbot/YandexBot/DuckDuckBot`. Схема: PTR-запрос → forward DNS → оба должны сойтись на официальный домен поисковика (`.googlebot.com`, `.search.msn.com` и т.д.).

Триггер на проверку — это сам поток логов: воркер видит запись с поисковым UA и IP, которого еще нет в каталоге `bot_verification_status` (ни как `verified`, ни как `rejected`), и ставит его в очередь. То есть это reactive, никакого превентивного перебора.

В каталог `bot_verification_status` публикуются оба исхода проверки:

- `verified` — оба DNS-этапа сошлись (TTL ~1 час).
- `rejected` — PTR/forward не сошлись или DNS вернул мусор (TTL ~1 час, симметрично с `verified`).

На proxy приходят обе категории — это нужно для L2.2 provisional fastpath (см. Этап 2.2): IP с поисковым UA, которого нет в каталоге ни в одном статусе, получает мягкий пропуск — для каждого запроса до тех пор, пока rDNS-воркер на backend не опубликует verified или rejected. После публикации финального статуса все следующие запросы с этого IP уже встречают либо `verified` (полный fastpath), либо `rejected` (нормальная обработка каскадом без fastpath).

На proxy — только set-membership lookup, никакого DNS в hot path.

**Доставка логов с proxy до приемника телеметрии.** Маршрут: proxy → backend → приемник телеметрии (ClickHouse или что выберем). Proxy с приемником телеметрии напрямую не общается — единственная исходящая интеграция proxy с нашей инфраструктурой это backend.

Почему двухступенчатая доставка:

- Proxy не хранят креды телеметрии и не знают ее endpoint — backend единственная точка интеграции; при смене storage'а proxy не трогаем.
- Backend — единая точка буферизации на случай недоступности приемника. На десятках proxy независимо буферизовать было бы менее надежно (потеря буфера при ребуте эдж-нода).
- Backend обогащает запись (например, добавляет `resource_id` клиента из своей БД по `host`).

Продуктовый контракт:

- Доставка не блокирует hot-path запроса на proxy.
- Если приемник телеметрии недоступен — логи не теряются (backend буферизует у себя до восстановления; буфер persistent).
- Если proxy не может достучаться до backend — на proxy есть локальный in-memory буфер на небольшое окно (секунды/минуты). При коротких сбоях backend'а ничего не теряется. При длительной недоступности (буфер переполнен) старые записи отбрасываются — приоритет на обработку запросов, hot-path не должен страдать ради логов. Метрика «процент потерянных логов на proxy» алертит если потери становятся регулярными.

#### Обновления каталогов и политики (триггер — клиент или продакт)

Это типовые повседневные изменения конфигурации. Все идут через тот же канал доставки каталогов, что и в постоянных процессах — отличается только источник изменения.

**Изменение per-resource policy** *(триггер — клиент в дашборде).* Клиент поправил Strictness, добавил custom UA-паттерн, добавил ASN в блоклист, переключил `attack_mode` для своего домена. Поток: dashboard → API backend → запись в БД → каталог `policy` обновляется → изменение применяется на proxy в пределах 30 секунд. Без передеплоя.

**Курация глобальных каталогов** *(триггер — продакт через PR).* Продакт регулярно смотрит аналитику и обновляет каталоги, общие для всех клиентов: добавил новый fp в `tls_fp_blocklist`, расширил `tls_fp_catalog` сигнатурами автоматизации, обновил `ua_blacklist`/`ip_blocklist`/`asn_datacenters`/`tls_fp_browser_profiles`. PR в наш репо → merge → backend обновляет каталог → применяется на proxy в пределах 15 минут.

Новые паттерны (которые могут давать false-positive на легитимном трафике) добавляются через staged rollout: сначала PR в `staging`-статусе (паттерн матчится и логируется, но не блокирует), наблюдение по логам, потом отдельный PR с промоутом в `active`. См. раздел «Staged rollout для PR-каталогов» в Конфигурации.

**Rollback каталога** *(триггер — продакт, когда что-то пошло не так).* Свежий PR оказался плохим (массовый false-positive после публикации — например, в `tls_fp_blocklist` попал fp, общий для всех Chrome). Лечение:

1. Продакт делает revert PR в репозитории каталогов.
2. Backend (source of truth) пересобирает свою версию каталога — фактически возвращается к прошлому состоянию.
3. Proxy (которые держат локальную реплику каталога в памяти для hot-path) подтягивают откаченную версию из backend в пределах 15 минут и атомарно подменяют shared_dict.
4. С этого момента все новые запросы на proxy матчатся уже против старой (рабочей) версии — инцидент закончился.

Никаких ручных операций ни на proxy, ни в БД — атомарная замена данных работает в любую сторону.

#### Аварийные рычаги (нештатные ситуации)

**Attack mode toggle.** Клиент в дашборде включает «Under Attack» для своего домена (per-host, глобального на пул нет) — запись попадает в `policy[host].attack_mode=true` → применяется на proxy в пределах 30 секунд. С этого момента каждый запрос на этот домен, дошедший до L5, идет через Этап 5.3 (challenge для браузеров, block для non-browser и unchallengeable). Cookie verify на L2.1 для этого host'a пропускается; verified search bots и IP-whitelist продолжают фастпасить.

**Kill-switch.** На каждом proxy всегда живет два тоггла:

- **Per-stage kill-switch** — выключает отдельный этап каскада (например, только `tls_fp` слой), если в нем обнаружили баг или перформанс-проблему. Остальной каскад продолжает работать.
- **Глобальный kill-switch** — выключает весь каскад целиком, Lua-модуль делает no-op, трафик идет мимо проверок (логов антибота нет). Страховка на случай катастрофы в самом каскаде.

**Кто переключает.** Kill-switch — операционный механизм уровня инфры, оператор всегда админ. У продакт-команды Bot & Abuse Controls нет self-service кнопки — при инциденте антибот-команда эскалирует админам с описанием, что именно выключить. Решение в защиту/выключение всего пула должно идти через тех, кто отвечает за инфру.

**Через что доставляется.** Channel A — Puppet (см. секцию «Конфигурация»). Изменение `defaults.conf` → Puppet-run по пулу → reload nginx. SLA — настолько быстро, насколько admin-команда может прогнать процедуру. 

**Когда применять:**

- Регрессия в логике каскада после релиза (баг в Lua, не в данных) — per-stage kill-switch для затронутого слоя, пока выпускаем hotfix.
- Перформанс-деградация на конкретном слое (выросла CPU/latency после раскатки нового слоя) — per-stage до разбора.
- Массовая неадекватная реакция, источник не локализован за приемлемое время — global kill-switch, разблокируем клиентов, разбираемся в логах в спокойном темпе.
- Catastrophic failure (Lua крашит worker'ы, OOM, бесконечный цикл) — global kill-switch немедленно.
- Плановый maintenance (крупная выкатка, миграция формата каталогов) — global на запланированное окно.

Защита от ботов не должна ронять сайты клиентов: если что-то пошло сильно не так — выключаемся, не блокируя обычный трафик.

## Архитектура — где что живет

Три исполнительных компонента, четко разделенные. Принципиально: весь hot-path — на proxy. Backend в обработке каждого запроса не участвует.

### Proxy — ВЕСЬ КАСКАД

**Что делает proxy на каждом запросе:**

- L1 Hygiene (метод, UA-blacklist)
- L2 Reputation (cookie verify, verified-bot lookup, IP whitelist/blocklist, ASN, гео)
- L3 Identity (TLS-fp compute + проверка по каталогам)
- L4 Behavioral rate-limits (sliding-window счетчики локально)
- L5 Active verification (выдача страницы challenge, проверка JS-задачи, подпись cookie)
- Сбор итогового JSON-лога и асинхронная отправка на backend

Все данные нужные для решений уже подготовлены локально в памяти proxy. Ни одного сетевого вызова к backend на каждом запросе. HMAC secret для подписи/проверки cookie тоже лежит на proxy.

**Чего на proxy нет:** никаких наших Go-процессов, никакого sidecar'а, ничего «рядом с nginx». Только Lua-каскад внутри самого nginx.

**Зона ответственности:** админы.

### Antibot-backend  — ТОЛЬКО КАТАЛОГИ, ЛОГИ, rDNS

**Что это:** сервис, развернутый на нашей инфраструктуре. Не на proxy. Не на hot-path. Proxy может его не достигать произвольно долго (fail-stale на последних каталогах).

**Три функции, ничего сверх:**

1. **Catalog-сервер.** Хранит все каталоги (`tls_fp_blocklist`, `tls_fp_catalog`, `ua_blacklist`, `ip_blocklist`, `ip_whitelist`, `asn_datacenters`, `tls_fp_browser_profiles`, `bot_verification_status`, `policy`) и поставляет их на proxy. Продуктовый контракт: задержка применения изменения ≤ 30 сек для быстрых каталогов (`policy`, `bot_verification_status`) и ≤ 15 мин для PR-каталогов (все остальное); атомарная замена без потери трафика; fail-stale на стороне proxy при недоступности backend. Конкретный механизм (БД, протокол доставки, кэширование) — на стороне backend-команды.
2. **Приемник логов.** Принимает поток JSON-строк с proxy, валидирует, батчит, шлет в приемник телеметрии (ClickHouse или что выберем). Внутренний disk-queue на случай если телеметрия лежит — логи не теряются.
3. **rDNS-воркер.** Единственная активная вычислительная задача backend'а. Фоновая горутина проверяет IP'ы с поисковыми UA через `PTR + forward DNS`, публикует результат (`verified` или `rejected`) в каталог `bot_verification_status`. Proxy на L2.2 использует это: `verified` — полный fastpath, `rejected` — обработка как обычно, отсутствует — provisional fastpath (см. Этап 2.2). Не на hot-path.
  **End-to-end SLA — best effort, без строгого числа.** «Время от первого pending-запроса с нового IP до публикации финального verified/rejected в каталоге» — типично секунды-минуты, но строгого продуктового SLA нет. Защита от запоздалой проверки уже встроена в дизайн: provisional fastpath не блокирует трафик, пока статус неизвестен. Если воркер деградирует — это видно по росту доли `bot_verified_pending` в логах, алертится по операционным метрикам.
   Семантика dedup/retry для воркера (как дедуплицировать IP в очереди, что делать с NXDOMAIN / SERVFAIL / timeout, политика ретраев) — на стороне backend-команды.

**Чего на backend НЕТ в v1:**

- Per-request scoring (grey-verdict callouts §В2 из RFC) — не используется
- ML / heavy analytics
- Per-request верификация чего бы то ни было — все на proxy

**Зона ответственности:** backend-команда.

### Dashboard.the platform.ru

**Что это:** клиентский кабинет, существующий компонент the platform.

**Что добавляем для Bot & Abuse Controls:** страница настроек ресурса (Challenge / Rate Limit Rules / Bot Lists / ASN Blocking) и аналитические виджеты. Детальное проектирование UI — в отдельной задаче, в этом документе не разбирается.

**Что делает:** редактирует per-resource policy через свой API. Изменения попадают в backend-БД → в каталог `policy` → применяются на proxy в пределах 30 секунд.

**Зона ответственности:** frontend-команда.

## Конфигурация — двухканальная модель

Два независимых канала доставки, разные ритмы.

### Channel A — Puppet (framework, медленный)

Несет:

- Lua source-файлы каскада (`verdict.lua`, `ja4_helpers.lua`, `log_emitter.lua` и т.д.)
- Секции nginx-конфигурации, регистрирующие hooks каскада и локальное хранилище под каталоги
- Kill-switch конфиг (глобальный и per-stage)
- **HTML+JS-шаблон challenge-страницы** — статический ассет, который proxy сервит при выдаче challenge; меняется редко, согласован по версии с Lua-каскадом
- **HMAC secret для clearance cookie** — общий для пула, грузится в proxy при старте nginx; ротация — новая версия через PR + reload nginx; ротация инвалидирует все ранее выданные cookie разом

Бинари не несет (на proxy их нет — никаких runtime-процессов антибота кроме самого nginx с Lua).

Ритм: PR в edge-puppet → ревью → Puppet agent run на эдж-нода. Минуты-часы. Это нормально — framework не меняется per request и per customer.

Fail-mode: если Puppet agent падает на эдж-нода — там остается прошлая версия framework'а. `nginx -t` блокирует битые конфиги до reload.

### Channel C — каталоги backend → proxy (runtime data, быстрый)

Несет все, что может меняться без передеплоя: blocklists, per-resource policy, attack_mode, verified-bot IP.

**Продуктовый контракт:**

- Задержка применения изменения на proxy — не более 30 секунд для быстрых каталогов (`policy`, `bot_verification_status`) и не более 15 минут для PR-каталогов (`tls_fp_blocklist`, `tls_fp_catalog`, `ua_blacklist`, `ip_blocklist`/`ip_whitelist`, `asn_datacenters`, `tls_fp_browser_profiles`) — с момента изменения в backend / merge'а PR.
- Замена данных на proxy — атомарная, без блокировок и потери трафика.
- При недоступности backend proxy продолжает работать с последней успешно загруженной копией каталога сколько угодно долго (fail-stale). Запрос клиента никогда не ждет обновления.
- **Битый каталог от backend → fail-stale на последней рабочей версии.** Если backend прислал каталог, который не проходит валидацию proxy (битая схема, неполный набор полей, заведомо bad data — например, миллион записей вместо ожидаемых тысяч), proxy применять его НЕ должен. Продолжает работать на последней успешно валидированной копии и инкрементит метрику «отвергнутых обновлений каталога»; backend-команда видит алерт.
- **Cold start (proxy запускается, каталоги еще не подтянулись).** В окне между стартом nginx и первой успешной загрузкой каталогов с backend каскад работает в режиме «пропускаю и логирую»: запрос идет мимо проверок в стандартный prod-edge-flow, в лог пишется специальный stage=`cold_start`, verdict=`pass`. Это окно — миллисекунды до десятков секунд, продуктово приемлемо. Альтернатива (ждать загрузки каталогов синхронно) ухудшает старт сервиса при инцидентах backend'а.
- Метрика staleness — алертит, если задержка превысила соответствующий SLA.
- **Per-host policy доставляется дельтами.** Каталог `policy` — это map `host → policy_json` с потенциально десятками тысяч записей. При изменении policy одного хоста backend публикует только эту запись (или маленький батч недавно измененных), proxy применяет дельту в свой shared_dict — без полной перевыкладки всего каталога. Это гарантирует, что изменение одного клиента не задерживается из-за объема каталога и что неверная запись одного хоста не блокирует распространение остальных. PR-каталоги остаются монолитными (они меньше и реже меняются).
- **Cross-proxy consistency — eventually consistent в пределах SLA окна.** Внутри окна SLA (≤30с для быстрых, ≤15мин для PR) разные proxy пула могут видеть разные версии каталога — это допустимо и заложено в дизайн. Строгая атомарность «все proxy одновременно» не требуется. Через окно SLA все proxy имеют одинаковую версию. Практическое следствие: после клика клиента в дашборде возможна короткая фаза, когда один и тот же IP блокируется на одних proxy и фастпасит на других; через 30 секунд состояние выравнивается.

Конкретный механизм (pull-таймер с proxy / push с backend / SSE / любой другой; HTTP/gRPC/что-то еще; ETag/version-vector/что-то еще) — на стороне команды.

### Staged rollout для PR-каталогов

**Проблема.** Часть PR-каталогов содержит паттерны (UA-регулярки, fp-сигнатуры, cipher-counts), которые могут давать false-positive на легитимном трафике. Если продакт добавит новую UA-регулярку через PR и через 15 минут она доедет до proxy — она сразу же начнет блокировать всех клиентов в `mode=active`. Если паттерн оказался слишком широким и задел легитимный браузер — массовый false-positive у платных клиентов одновременно.

**Решение — staging-статус паттернов.** Каждая запись в каталоге имеет поле `status` с двумя значениями:

- `staging` — паттерн загружен на proxy, proxy его матчит и пишет факт срабатывания в лог (специальное поле, например `staging_match: ["ua_blacklist:pattern_123"]`), но не приводит к `verdict=block` даже в `mode=active`. То есть verdict у такого запроса в логе остается таким, как был бы без этого паттерна. По факту запрос идет дальше через каскад как обычно.
**Формат `pattern_id`** — стабильный идентификатор записи в каталоге, который продакт указывает в PR. Соглашение по каталогам:
  - `ip_blocklist`, `ip_whitelist` — `pattern_id` = сам IP/CIDR (`ip_blocklist:192.0.2.5`, `ip_whitelist:10.0.1.0/24`).
  - `ua_blacklist` — `pattern_id` = человекочитаемый ID (продакт пишет в PR, например `ua_blacklist:scrapy_v2_2026_05`).
  - `tls_fp_blocklist` — `pattern_id` = сам fp-токен (`tls_fp_blocklist:L1300_a8b9c..._d4e5f...`).
  - `tls_fp_catalog` — `pattern_id` = `hash_b` запись (тот же hash_b, что в каталоге).
  - `tls_fp_browser_profiles` — `pattern_id` = `browser_family` (`tls_fp_browser_profiles:chrome`).
  - `asn_datacenters` — `pattern_id` = сам ASN номер (`asn_datacenters:AS16509`).
  Backend гарантирует стабильность `pattern_id` между релизами каталога (один и тот же паттерн → один и тот же ID).
- `active` — паттерн полноценно работает: matches → `verdict=block` в `mode=active`, как и сегодня.

**Workflow для продакта при добавлении нового паттерна:**

1. **PR с паттерном в `staging`**. 15 минут — паттерн доехал до proxy.
2. **Наблюдение по логам.** Сколько раз новый паттерн сработал (`staging_match`), на каких клиентах, какой профиль трафика, выглядит ли как реально плохой или это false-positive.
3. **Решение по результатам:**
  - FP-rate приемлемый → отдельный PR: переводит паттерн из `staging` в `active`. Еще 15 минут — паттерн начинает блокировать.
  - FP-rate высокий → revert PR из этапа 1. Паттерн исчезает с proxy.

**Какие каталоги поддерживают staged rollout:**


| Каталог                    | Staging | Почему                                                                                                             |
| -------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------ |
| `ua_blacklist`             | ✅       | Новая UA-регулярка может задеть легитимный браузер/SDK                                                             |
| `ip_blocklist`             | ✅       | Новый IP может оказаться легитимным API-клиентом                                                                   |
| `tls_fp_blocklist`         | ✅       | Новый fp может оказаться новой версией реального браузера                                                          |
| `tls_fp_catalog`           | ✅       | Новая impersonator-сигнатура может ложно матчить браузер                                                           |
| `tls_fp_browser_profiles`  | ✅       | Изменение ожидаемого cipher_cnt может задеть актуальные браузеры                                                   |
| `asn_datacenters`          | ❌       | Источник для информационного тега `reputation:asn_dc`, не для правила. Тег не блокирует — staged rollout не нужен. |
| `ip_whitelist` (системный) | ❌       | Whitelist пропускает, не блокирует — низкий риск                                                                   |
| `policy` (per-resource)    | ❌       | Клиент сам тестирует через временный `mode=shadow` для своего ресурса                                              |
| `bot_verification_status`  | ❌       | Не паттерн (автоматическое наполнение rDNS воркером)                                                               |


**Семантика логирования при staging-матче:**

Запрос идет через каскад как обычно — staging-паттерн НЕ обрывает поток, НЕ блокирует, НЕ влияет на `verdict`. Но в логе появляется дополнительное поле `staging_match` со списком сработавших staging-паттернов:

```json
{
  "verdict": "pass",
  "rule": "",
  "staging_match": [
    "ua_blacklist:new_pattern_2026_05_18",
    "tls_fp_blocklist:fp_L13d11h2_xxx"
  ],
  ...
}
```

Так продакт по логам может строить аналитику: «новый паттерн `ua_blacklist:new_pattern_2026_05_18` за сутки матчился N раз, из них на платных клиентах X, ratio к их общему трафику Y%» — и принимать обоснованное решение о промоуте.

**Что не покрывает staged rollout:**

- **Очень редкие паттерны** (срабатывают раз в неделю) — за сутки наблюдения статистика может быть пустой. Здесь продакт принимает решение по уверенности в источнике паттерна, не по статистике.
- **Per-resource ситуации** — staging применяется глобально. Если паттерн делает FP только для одного конкретного клиента — это видно в логах, и клиент может добавить exclusion в свою `policy` (custom whitelist), но сам staging это не разделяет.

### Lookup ключ — Host, не resource_id

На proxy доступен `Host` запроса напрямую (из HTTP-заголовка). Каталог `policy` — это map `host → policy_json`. Lookup тривиальный, никакой дополнительной мапы `Host → resource_id` поверх не нужно.

### Что НЕ каталог

**Rate-counters, verdict cache, TLS-fp cache** — это локальные per-proxy состояния: живут только в памяти на каждом proxy, никем не централизуются. Правило простое: если все proxy должны видеть одно значение в один момент → каталог. Если это per-proxy runtime state → локально на proxy, в каталог не публикуется.

Включать enforce глобально без этой развязки нельзя — это коснулось бы всех клиентов одновременно, включая бесплатных. Поэтому Phase 4 невозможен без Phase 3, а Phase 5 — это продуктовое решение о коммерческом запуске, не следующая техническая ступень.

## Технические гарантии и ограничения

### Latency

- **Verdict pipeline на proxy:** ~µs–десятки µs (HMAC verify, shared_dict lookup, GCRA).
- **Catalog pull:** в фоне, не на hot path. Proxy не блокирует обработку запроса на pull'е.
- **Challenge (L5):** 1–3 секунды в браузере на выполнение JS-задачи.

### Ложные срабатывания

JS challenge может некорректно срабатывать на:

- Headless browsers в легитимных сценариях (e2e тесты, uptime-мониторинг)
- Корпоративные proxy, изменяющие заголовки
- Очень старые браузеры без поддержки Canvas / WebGL

TLS-fingerprint impersonator может ложно срабатывать на:

- Новых версиях браузеров с обновленным TLS-стеком (cipher_cnt сдвинулся) — пока не обновили `tls_fp_browser_profiles`
- Корпоративных proxy с собственным TLS-стеком

Решение: переключить Strictness в Permissive (системные soft-flags не триггерят challenge), добавить IP/fp клиента в per-resource whitelist.

### Доступность

**Proxy:** если наш код каскада упал (баг, исключение в обработке запроса) — глобальный kill-switch выключает каскад целиком, трафик идет мимо проверок.

**Antibot-backend:** если недоступен — proxy продолжает работать с последним хорошим catalog'ом (fail-stale). Метрики staleness дают alerting. ≥ 2 инстанса backend'а делают этот режим редким.

**Сеть proxy → backend:** прерывание подключения — то же fail-stale. Никакого влияния на hot path.

### Данные

IP-адреса, User-Agent, TLS-fingerprint и метаданные запроса обрабатываются в памяти на proxy. Долгосрочно на proxy не хранятся. Clearance cookie живет только в браузере пользователя.

Логи передаются на backend → приемник телеметрии (ClickHouse или аналог), хранение по политике ретеншена.

Browser fingerprint, собираемый во время JS challenge (User-Agent, разрешение экрана, Canvas, WebGL, AudioContext), проверяется на непротиворечивость в момент прохождения challenge, а затем уезжает в backend как часть challenge-pass-события и хранится в той же телеметрии. Для верификации последующих запросов (там работает clearance cookie) и для отслеживания пользователей между сайтами он не используется — после проверки консистентности собирается как датасет для долгосрочной аналитики и будущих ML-моделей (L6, OOS v1).

## Что прямо не входит в v1 и почему

Фиксирую, чтобы не было лишних ожиданий:

- **Headless browser detection (L6+).** Нужен JS-биакон с поведенческими сигналами (mouse, timing) — это другой продукт.
- **Residential proxy detection.** Трафик идет с легитимных домашних IP, отличается только по поведению — нужен L6+.
- **Поведенческий ML на сессиях.** L6+. Out of scope v1.
- **HTTP/2 fingerprinting.** Дополнительный сигнал клиента — порядок SETTINGS frames, window updates, priority frames. Аналог L3 для HTTP/2-слоя. Будущая задача, не v1.
- **Глобально точный rate-limit cross-proxy.** В v1 лимиты per-proxy (worker). Глобальная точность требует Redis Cluster или аналога — v2.
- **Per-request callouts с proxy на backend для расчета вердикта.** В v1 нет heavy/ML логики, поэтому per-request вызов с proxy на backend не нужен. Если когда-нибудь появится — потребует пересмотра архитектуры (вероятно, добавление тонкого per-proxy sidecar для этого слоя). Сейчас не нужно.
- **Per-resource политики TLS-fp.** В v1 каталог fp общий для всех ресурсов. Дифференциация (у B2B-API клиента ожидаемые TLS-стеки отличаются от публичного сайта) — последующие итерации.
- **Активная автоматическая верификация ML.** Все challenge-сигналы пока ручные / правила. Автоматическое продвижение HIGH-кандидатов в blocklist — отдельная задача со своими гарантиями false-positive.
- **API-key whitelist для не-браузерных клиентов.** В v1 единственный способ для серверной/мобильной интеграции клиента избежать challenge — добавить ее IP в IP-whitelist (Этап 2.3). Для клиентов с динамическими IP (контейнеры, serverless, мобильные приложения) это неудобно. API-key whitelist (клиент создает секретный ключ в дашборде, его интеграции передают ключ в HTTP-заголовке, proxy фастпасит) — кандидат на следующую итерацию. Требует: backend (генерация/хранение/хеширование/ротация/revoke ключей), UI в дашборде (создание/список/revoke), маскирование ключей в логах, документация для клиента. Сложность сопоставима с самой policy-страницей.

## Что нового в v0.5 (changelog от v0.4)

Итерация поверх v0.4 по результатам обсуждения. Позиционирование, режимы и бизнес-семантика сохранены; уточнены спорные места, добавлен верхнеуровневый обзор и согласована терминология между документами.

Главное:

1. **Добавлен раздел «Обзор продукта»** в начале — верхнеуровневое описание для коллег: что это, из чего состоит (proxy + backend), что такое каскад, что такое правило (rule) и тег в нашей терминологии, политики и режимы. Плюс «кому это нужно» и «чем не является».
2. `**attack_mode` — только per-host.** Глобального тоггла на пул больше нет (для инфра-уровня — kill-switch). Под атакой clearance cookie, выданные до начала атаки, не фастпасят (выданные во время атаки — да); verified bots и IP-whitelist фастпасят. Non-browser и протокольно несовместимые запросы под атакой блокируются (ветки B/C), а не идут на challenge.
3. **Новый verdict `permissive`.** Когда системные soft-flags подавлены режимом Strictness=Permissive, в лог пишется `verdict=permissive, rule=<последний soft-флаг>` — отличает «прошел, потому что Permissive» от «прошел, потому что чисто».
4. `**should_challenge()` описан как вычисляемая на L5 функция** (от attack_mode + накопленных флагов + Strictness), а не как записанный флаг.
5. **Новое правило `unchallengeable_request`** (ветка C): запрос протокольно несовместим с JS challenge (не GET, WebSocket, `Accept` без `text/html`).
6. **Новый тег `hygiene:header_anomaly`** (L1): аномальные комбинации заголовков (HTTP/2 без `Accept`). Информационный, не блокирует.
7. **Rate-limits — зафиксирован GCRA.** Клиентские rate-rules проверяются раньше системных; код правила `rate_custom` + поле лога `client_rule_name` (уникально в пределах host).
8. **Атрибуты clearance cookie** заданы явно (HttpOnly / Secure / SameSite=Lax / Path / Domain). Cross-proxy challenge через self-signed nonce. Ротация HMAC secret: плановая через Puppet + аварийный admin-плейбук. TTL cookie — системная константа (24ч / 1ч под атакой).

8b. **Лог-поле `flags`.** В лог добавлен массив всех накопленных по пути challenge-флагов (soft-правила) — отдельно от терминального `rule`. Закрывает обещание обзора «запись лога с правилом, флагами, тегами» и даёт аналитику со-встречаемости сигналов.
8a. **Clearance-cookie — частичный фастпас, а не полный.** Держатель валидной cookie пропускает L3 (TLS-fp) и L5 (challenge), но проходит через L4 (rate-limits) — cookie не дает права злоупотреблять (брутфорс/скрейпинг). Полный фастпас (skip L3-L5) остается только у verified-bot и IP-whitelist. Закрывает дыру «решил challenge один раз → долблю rate-free весь TTL cookie».
9. **rDNS уточнен:** `rejected` TTL 5м → 1ч; `bot_family` для rejected = UA-claimed; `bot_verified_pending` срабатывает на каждый запрос, пока backend не опубликует статус.
10. `**resource_id`** проставляет backend при приеме лога (proxy работает только с `Host`).
11. **Скоуп: домены edge-пула без записи в policy** работают на системных дефолтах (shadow), policy — это override. Per-host policy доставляется дельтами; cross-proxy consistency — eventually consistent в пределах SLA.
12. **Поведение при сбоях:** cold start = пропуск + лог (stage `cold_start`); битый каталог от backend → работа на последней рабочей версии.
13. **Kill-switch** — операционный механизм prod-edge-админов (не self-service продакта).
14. **Согласованы сопутствующие документы:** добавлены [rules-reference.md](rules-reference.md) (плоский каталог правил) и [config-templates.md](config-templates.md) (шаблоны конфигов). Переименование поля policy `asn_blocklist` → `asn_block`. Бэклог в ClickUp синхронизирован по `attack_mode` и rDNS TTL.

## Что нового в v0.4 (changelog от v0.3)

Документ итерируется поверх v0.3 — позиционирование, режимы, бизнес-семантика всех фич сохранены. Главное структурное изменение: документ теперь сфокусирован на подкапотном end-to-end traffic path (от приема запроса на proxy до доставки клиенту из кеша или с origin) — это то, что нужно командам для проектирования бэкенда и интеграции с proxy.

UI клиентского дашборда (как клиент видит свою аналитику, покупает защиту, настраивает Strictness) — отдельная задача, в этом документе не разбирается. Считаем, что клиент уже купил, его политика лежит в нашей базе и доехала до proxy.

Что изменилось:

1. **Архитектура переосмыслена.** v0.3 описывал монолитный sidecar-процесс на каждом proxy, который nginx звал на каждом запросе. Это устарело. Чистое разделение: proxy выполняет ВЕСЬ каскад L1–L5 на каждом запросе локально; antibot-backend — только источник каталогов, приемник логов и фоновый rDNS-воркер. Backend на hot-path не находится. Никаких упоминаний устаревшей архитектуры в тексте не осталось.
2. **Добавлена 6-уровневая модель защиты L1–L6.** Раньше фичи были плоским списком; теперь каждая четко относится к слою, и видно куда упирается scope v1 (L5) и что осталось за скобками (L6+).
3. **Раздел «Как это работает» переписан как end-to-end traffic flow.** От TLS-handshake → каскад L1–L5 → cache lookup → origin fetch → доставка ответа → запись лога. Явно показано, что антибот применяется до cache lookup, и что prod-edge в edge-пуле — полноценный CDN, не просто proxy. Описано, что происходит при `verdict=block/challenge` (прерывание потока, 403/429/challenge-страница). Скоуп явно сужен: рассматриваем только трафик на защищенные клиентские домены, не-наш трафик — зона prod-edge-админов.
4. **Раздел «Фичи» удален.** Все продуктовые фичи (Scoring/Strictness, Rate-limit presets, JS Challenge, Clearance cookie, Verified Bots, Bad-bot blocklist, ASN-блок, Under Attack mode, TLS-fingerprinting) описаны внутри соответствующих этапов каскада.
5. **TLS-fingerprinting (Phase 2)** добавлен как L3 каскада. В v0.3 этого слоя не было.
6. **Раздел «Как выглядит в дашборде» удален.** UI-скоуп выносится в отдельную задачу; в этом документе только пометка о наличии дашборда.
7. **Раздел «Что работает в фоне и параллельно»** — собран в одном месте, три категории: постоянные фоновые процессы (pull каталогов, rDNS-воркер, доставка логов), обновления каталогов и политики по триггеру клиента/продакта (изменение policy, курация, rollback), аварийные рычаги (attack mode, kill-switch). Раньше все это было размазано по разным секциям.
8. **Объяснено фазирование** (Phase 1 observe-only → Phase 2 TLS-fp → Phase 3 backend+dashboard → Phase 4 active verification → Phase 5 enforce + монетизация). В v0.3 продукт описывался как уже работающий; теперь явно: в Phase 1/2 каскад только наблюдает.
9. **Конфигурация — двухканальная модель** (Puppet framework + наш catalog HTTP pull). Lookup по `Host`, не по `resource_id`. Закрывает «open question» из Phase 1.
10. **Зоны ответственности команд** — новая отдельная секция, чтобы документ можно было отдать на ревью с явным указанием, кто что делает.
11. **Технический раздел про потребление ресурсов** переписан под новую топологию: на proxy мы Go-процессов не запускаем.
12. **Сравнение с Cloudflare** дополнено строкой про TLS-fingerprinting.

Что не изменилось:

- Позиционирование («не enterprise-антибот, ~80% типичных SMB кейсов»)
- Режимы shadow / active (раньше были Off / Standard / Under Attack — упростились до двух + отдельный тоггл Under Attack как флаг поверх active)
- Бизнес-семантика всех фич (но переехала в «Как это работает» на места своих слоев)
- Что прямо не входит в v1 (расширено, но не сокращено)

Что вынесено в другие задачи:

- UI клиентского дашборда и аналитические виджеты
- Feedback-петли (как продукт калибрует пороги по логам, как клиент видит свою аналитику)
