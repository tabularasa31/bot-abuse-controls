# Аналитика и жизненный цикл блок-листа — спецификация (пост-MVP)

**Версия:** v1.0 · **Статус:** проектный контракт (целевое поведение) · слой пост-MVP

Этот документ описывает **целевое поведение оффлайн-плоскости аналитики**: как из
потока вердиктов каскада ([vision.md](vision.md)) система выводит, какие
TLS-отпечатки безопасно блокировать, проводит их через управляемый жизненный цикл
и доставляет результат обратно на эдж в виде каталога. Это спецификация «бери и
делай»: по ней строится реализация, как каскад строится по vision.

Каскад из vision — это **горячий путь**: решение по каждому запросу за микросекунды
по каталогам, уже лежащим в памяти. Этот слой — **обратная связь**: он наполняет и
поддерживает один из этих каталогов (`tls_fp_blocklist`), опираясь на то, что
каскад уже наблюдал.

**Сопутствующие материалы (как у vision):**
[analytics-rules-reference.md](analytics-rules-reference.md) — правила скоринга,
гейтов и жизненного цикла в формате «если условие → действие»;
[analytics-entities-reference.md](analytics-entities-reference.md) — словарь
сущностей (score, гейты, тиры, каталожная запись, артефакты, состояние,
перечисления).

---

## 1. Что это

Плоскость, которая **замыкает петлю** между наблюдением и enforcement:

```
   эдж (каскад) ──поток вердиктов──► аналитика ──► скоринг ──► решение
        ▲                                                        │
        │                                                        ▼
        └──── доставка каталога ◄──── автомат / человек ◄── каталог (PR)
```

Эдж на каждом запросе эмитит структурный вердикт. Поток вердиктов стекается в
лог-хранилище. Этот слой читает хранилище, строит картину по каждому
TLS-отпечатку, **ранжирует** подозрительные отпечатки, **решает** через
гейты-вето, какие безопасно блокировать, проводит их по **жизненному циклу**
(staging → наблюдение → active → снятие) и **доставляет** результат обратно на
эдж через каталог блок-листа.

Цель — превратить наблюдения каскада в его же конфигурацию: автоматически,
объяснимо и обратимо, с человеком только на финальном «да».

## 2. Из чего состоит

| Компонент | Роль |
| --- | --- |
| **Аналитический воркер** | читает поток вердиктов за окно, строит per-fp агрегаты, считает score и гейты, пишет артефакты решений, шлет ежедневный отчет |
| **Модель скоринга** | аддитивный score (ранжирование) + гейты-вето (допуск) + intent-правило |
| **Сигналы детектора** | позитивный каталог браузеров, UA↔fp mismatch, headless-каталог, challenge solve-rate, поведенческие сигналы — повышают точность score |
| **Робастность (anti-poisoning)** | защита purity-вето и скоринга от целенаправленного загрязнения |
| **Менеджер жизненного цикла** | переходы записи блок-листа: candidate → staging → active → снятие |
| **Автомат** | собирает созревшие изменения в один draft-PR за прогон; никогда не мержит |
| **Состояние** | персистентный аккумулятор lifetime-сигналов + его ротация |

## 3. Чем НЕ является

- **Не горячий путь.** Этот слой никогда не вызывается в обработке запроса. Его
  недоступность не влияет на латентность и доступность каскада — эдж работает на
  последней доставленной копии каталога (fail-stale).
- **Не enforcement.** Слой не блокирует трафик сам. Он редактирует каталог;
  блокирует — каскад, по доставленному каталогу.
- **Не ML.** Детерминированный скоринг по объяснимым сигналам с жесткими гейтами.
  Каждое решение разворачивается в человекочитаемый паспорт.
- **Не автономен.** Автомат готовит draft-PR; финальное «да» дает человек через
  ревью. Прямого пути «аналитика → блокировка» без человека нет.

## 4. Принцип в одном экране

- **Эдж — producer наблюдений, этот слой — consumer.** Граница — лог-хранилище.
  Все, что слою нужно знать о реальности, он берет из потока вердиктов, а не из
  живого трафика.
- **Score только ранжирует. Допуск решают гейты.** Высокий score сам по себе
  ничего не блокирует; низкий — не мешает попасть в отчет человеку.
- **Наблюдение важнее прогноза.** Прежде чем блокировать, отпечаток наблюдается в
  observe-only режиме на живом трафике; активация — по факту чистого наблюдения,
  не по исходному прогнозу.
- **Снятие так же автоматизировано, как постановка.** Человек не отследит, какой
  отпечаток перестал быть угрозой; это делает автомат по неактивности.
- **Каждое изменение каталога — через PR с аудит-паспортом.** Никакого прямого
  SQL/admin-UI к блок-листу: причина, evidence, гейты и план жизненного цикла
  фиксируются в PR и в комментарии-паспорте над записью.

## 5. Контракт входа — поток вердиктов

Слой потребляет один структурный вердикт на каждый обработанный запрос. Это
**единственный** вход: вся картина строится из этого потока, отдельной телеметрии
слой не заводит. Минимально необходимые поля контракта (стабильны между
итерациями):

| Поле | Смысл для слоя |
| --- | --- |
| `tls_fp` | ключ всего анализа; агрегация идет по нему |
| `ip` | число уникальных IP, multi-IP сигнал, сверка с allowlist |
| `ua` | классификация automation / impersonator / genuine-browser |
| `path` | recon-URI сигнал |
| `verdict` | детект identity-allow (любой `allow` → allowlist-вето) |
| `rule` | какое правило сработало (атрибуция) |
| `staging_match` | список staged-паттернов, сматчившихся в observe-only |
| `asn` / тип ASN | datacenter-ASN сигнал |
| метка времени | окно наблюдения, число разных дней, persistence |

**Горизонт хранилища vs горизонт решений.** Хранилище вердиктов хранит ограниченное
окно (порядок недели). Решения слоя выходят за этот горизонт (снятие по
неактивности измеряется неделями), поэтому слой ведет **персистентный аккумулятор**
(см. §11): то, что хранилище уже забыло, берется из него.

## 6. Отпечаток (fp)

Клиент при TLS-рукопожатии шлет ClientHello: список шифров, расширения, версии — в
определенном порядке. Каскад сворачивает это в строку-отпечаток фиксированного
формата (см. vision). Ключевое свойство для этого слоя:

**Внутри одного отпечатка число шифров (`cipher_count`) и хеши фиксированы** — это
часть токена. Реальные браузеры предлагают число шифров из узкого набора (по
наблюдениям — `{15, 16, 20}`); инструменты-автоматизаторы — другое. На этом
расхождении стоит purity-вето: «UA говорит браузер» при «почерк не браузерный» =
маскировка.

## 7. Модель скоринга

Ядро слоя. Решение «блокировать ли отпечаток» состоит из **двух независимых
слоев**, которые нельзя смешивать.

### 7.1 Score — ранжирование (аддитивно)

**Score отвечает на вопрос «насколько это похоже на бота».** Сумма сигналов, нужна
только чтобы отсортировать кандидатов в отчете. Сама по себе **ничего не блокирует**.

| Сигнал | Очки | Смысл |
| --- | --- | --- |
| impersonator | **+3** | браузерный UA на отпечатке известного инструмента (маскировка) |
| suspicious cipher | +1 | число шифров вне браузерного набора при браузерном UA |
| automation UA | +1 | UA сам по себе инструмент (curl/python/go/okhttp/bot/scanner) |
| datacenter ASN | +1 | хотя бы один IP в datacenter-ASN |
| multi-IP | +1 | ≥2 разных IP под одним отпечатком |
| persistent | +1 | отпечаток виден ≥2 разных дней |
| recon URI | +1 | обращения к типовым recon-путям (`/.env`, `/wp-login`, …) |

Тиры: **HIGH ≥5 · MEDIUM 3–4 · LOW 1–2.**

`impersonator` весит больше прочих намеренно: он опирается на словарь известных
инструментов — высокая точность. `suspicious cipher` весит мало: слабая эвристика,
ложащаяся на нетипичных, но легитимных браузерах.

### 7.2 Gates — допуск (вето, не складываются)

**Гейты отвечают на вопрос «безопасно ли это блокировать».** Это пороги-вето: score
может быть сколь угодно высоким — если хоть один гейт не пройден, промоута нет.
Гейты НЕ суммируются и НЕ компенсируют друг друга.

| Gate | Условие | Зачем |
| --- | --- | --- |
| **purity** (вето) | доля «настоящих браузеров» ≤ порога | под отпечатком не ходят живые люди |
| **volume** | достаточно событий и хотя бы один IP | отсечь шум на единичных запросах |
| **allowlist** (вето) | ни одного allow-вердикта, ни одного IP в whitelist | не блокировать легитимный/verified трафик |
| **dedup** | отпечатка еще нет в каталоге | идемпотентность |
| **intent** | impersonator ИЛИ (recon И не generic_honest_tool) | не блокировать общий отпечаток инструмента |

### 7.3 Два разных риска ложного блока

Это ключ ко всему дизайну. Заблокировать отпечаток по ошибке можно **двумя разными
способами**, и закрываются они **разными механизмами** — поэтому purity и intent
существуют отдельно.

**Риск 1: «неизвестный легитимный браузер приняли за бота» → purity-вето.**
Считаем долю событий, которые выглядят как настоящий браузер. Событие = *genuine
browser*, если **одновременно**: UA браузерный, число шифров браузерное, и хеши
отпечатка не из словаря инструментов. Если доля таких событий выше порога —
блокировать нельзя при любом score: под отпечатком ходят живые люди. Три условия
вместе потому, что UA подделать легко, а почерк рукопожатия — труднее: «UA = Chrome,
почерк = curl» считается маскировкой, а не человеком.

**Риск 2: «заблокировали общий отпечаток инструмента» → intent-правило.**
Отпечаток самого `curl` (или python-requests) **общий для всех его пользователей в
мире**: мониторинги, CI/CD, healthcheck'и, легитимные API-клиенты. recon-запросы от
одного актора **не делают общий отпечаток безопасным** — и purity тут не спасает
(браузерных событий нет, human_share = 0). Блок такого отпечатка отрезал бы
всю легитимную автоматизацию. Поэтому авто-блок оправдан только при **намерении,
специфичном для самого отпечатка**:

- **impersonator** — браузерный UA на инструментальном отпечатке: сочетание само по
  себе аномально, отпечаток «притворщика» специфичен → блок безопасен;
- **recon на не-generic отпечатке** — recon-запросы под отпечатком, который не
  является известным honest-инструментом: неизвестный сканерный отпечаток с recon —
  специфичная сигнатура → блок безопасен.

Честный `curl` с recon → намерение не выполнено → автомат его не трогает; это кейс
для блок-листа по UA или IP (адресно), его решает человек.

### 7.4 auto_eligible

Кандидат пригоден для автоматического промоута, если: тир HIGH, отпечаток виден
достаточно дней, **все** гейты пройдены, и выполнено intent-правило. Только такие
кандидаты автомат предлагает в draft-PR на `staging`. Остальное (HIGH без intent,
MEDIUM, LOW) остается в отчете на усмотрение человека.

Порог «дней до входа» намеренно низкий: `staging` — observe-only (см. §9), поэтому
проверять устойчивость до входа смысла мало; настоящий полигон — окно наблюдения
`staging → active`, а блипы-однодневки отсекает volume-гейт.

## 8. Сигналы детектора (повышение точности)

Score из §7.1 — базовый набор. Слой расширяется дополнительными сигналами, каждый
из которых либо добавляет очки, либо ужесточает/смягчает гейт. Все они описаны как
**целевое поведение**; ни один не обязателен для базовой петли, но каждый повышает
точность.

- **Позитивный каталог браузеров (version-labeled).** Справочник «известный-хороший»:
  какие хеши принадлежат каким семействам и версиям браузеров. Дает (а) точную
  проверку genuine-browser, (б) **known-good инвариант** (§9.x / robustness): отпечаток,
  совпавший с позитивным каталогом, **никогда** не авто-блокируется. Развивается от
  семейство-уровневого (family → ожидаемое число шифров) к version-labeled
  (hash → family + версия).
- **UA↔fp version mismatch.** Если UA заявляет «Chrome 148», а почерк отпечатка
  соответствует другой версии/семейству — это сигнал маскировки **без** словаря
  инструментов (расхождение вместо impersonator-словаря). Опирается на позитивный
  каталог.
- **Headless-каталог.** Отпечатки headless-стэков (Playwright / Puppeteer /
  undetected-chromedriver): автоматизация, прикидывающаяся браузером, со своим
  узнаваемым почерком.
- **Challenge solve-rate.** Доля решенных challenge по отпечатку: отпечаток, который
  массово получает challenge и почти никогда его не решает при достаточном числе
  выданных — near-ground-truth метка бота, сильнее любой статической эвристики.
  Используется и как доп-сигнал score, и как ускоренный гейт перехода
  `staging → active`.
- **Поведенческие / временные сигналы.** Межзапросные интервалы (ритмичность),
  отсутствие человеческого разброса, навигационные графы (бот ходит по recon/sitemap,
  не по ссылкам). Переводят детект из сигнатурного в поведенческий — рычаг против
  low-and-slow ботов, которые проходят rate-limit и не светят инструментальный
  отпечаток.

## 9. Жизненный цикл записи блок-листа

Каждый отпечаток проходит управляемый путь от кандидата в отчете до enforcement и
обратно. Между прогнозом и блокировкой всегда есть фаза наблюдения на живом
трафике.

```
   кандидат в отчете
        │ promote (прогноз: HIGH + gates + intent)
        ▼
     staging ──набл. ≥окна, ноль ложняков, ≥минимума матчей──► activate ──► active
        │ задел живой браузер → флаг demote/remove                          │ молчит > TTL
        └──────────────────────────────────────◄────────────────────────────┘
                                  auto-demote: active → staging → remove
```

### 9.1 Состояния каталога

Каталог блок-листа хранит per-fp статус ∈ `{staging, active}`. Над каждой записью —
комментарий-паспорт (причина, score, evidence, human_share, дата ревизии).

| Статус на эдже | Поведение каскада |
| --- | --- |
| `staging` | **match-but-observe**: эдж матчит отпечаток, отмечает `staging_match`, **НЕ блокирует** |
| `active` | **enforce**: блокировка (403), правило `tls_fp_blocklist` |
| (нет записи) | каскад отпечаток не знает |

### 9.2 Переход candidate → staging (promote)

Триггер — прогноз: HIGH + все гейты + intent. Открывается PR со статусом `staging`.
Гейты — жесткие вето (purity/allowlist не перебиваются). После merge запись
доставляется на эдж и начинает матчиться в observe-only. Смысл фазы: дать наземную
правду о ложняках **до** enforcement.

### 9.3 Переход staging → active (activate)

Триггер — **подтверждение наблюдением**, не исходный прогноз. По событиям, где
сматчился staged-паттерн отпечатка, за окно наблюдения:

| Гейт | Условие | Зачем |
| --- | --- | --- |
| окно | в staging не меньше минимального числа часов | застать разный суточный трафик |
| объем | не меньше минимума матчей | иначе судить не о чем |
| ноль ложняков (вето) | human_share среди матчей = 0 | задел живой браузер → НЕ активировать |
| allowlist re-check | среди матчей нет whitelist/verified | перепроверка на реальном трафике |

Вердикты наблюдения: **activate** (все ок → PR `staging → active`), **fp_caught**
(наблюдение поймало легитимный трафик → кандидат на снятие, активацию НЕ предлагаем),
**observe** (мало матчей/времени → наблюдаем дальше).

### 9.4 Auto-demote (снятие по неактивности)

Человек не отследит, какой отпечаток перестал быть угрозой, поэтому это делает
автомат. «Последний раз виден» берется из персистентного аккумулятора (он живет
дольше горизонта хранилища вердиктов). Если отпечаток молчит дольше TTL —
кандидат на снятие. **Двухступенчато:** `active → staging` (молчит) → `staging →
remove` (снова молчит). Записи без истории наблюдения автомат не трогает —
оставляет человеку.

TTL здесь — **не** enforced-протухание на эдже (его в каталоге нет), а порог
неактивности для авто-детектора снятия.

### 9.5 Ручное снятие (обратимость)

Любой переход откатывается адресно (снять отпечаток: `active → staging` или
удалить) либо целиком (revert PR). Все в рамках SLA доставки каталога.

## 10. Автоматизация

Автомат превращает суточные артефакты решений в **ОДИН draft-PR за прогон**.
Контракт:

- **Никогда не мержит. Никогда не открывает не-draft PR.** Человек ревьюит и мержит.
- **Двунаправлен.** В одном PR — все созревшее: promote HIGH → staging; activate
  staging-записей с чистым наблюдением; demote молчащих (active→staging,
  staging→remove).
- **Один PR за прогон.** Все изменения батчатся в одну ветку/PR — не шум из
  десятков PR.
- **Идемпотентен.** Повторный прогон в тот же период не плодит дубли (гейт на
  существование уже открытого PR).
- **Freshness guard.** Артефакты несут метку времени генерации; если они устарели
  (воркер лежит) — автомат не действует на старых данных.
- **Чистое состояние при любом исходе.** Прерывание на середине откатывает правки
  каталога.

PR-тело — паспорт по секциям (promote / activate / demote), каждая строка с score,
тиром, evidence, human_share, датой ревизии.

## 11. Артефакты, состояние, ротация

**Артефакты решений.** Воркер на каждом прогоне пишет машинно-читаемые срезы:
ранжированные кандидаты (score, тир, гейты, auto_eligible), наблюдение за staging
(матчи, human_share, часы, вердикт), кандидаты на снятие (молчание, флаги).
Потребители (промоут-инструмент, автомат) читают только эти артефакты. Каждый несет
метку времени генерации (для freshness guard).

**Персистентный аккумулятор.** Нужен ровно для того, что хранилище вердиктов за свой
горизонт не помнит: накопленный объем событий (для volume-гейта) и «последний раз
виден» (для снятия по неактивности, чей TTL больше горизонта хранилища). Ключ —
отпечаток.

**Ротация состояния.** Аккумулятор растет — ротация ограничивает рост: старые записи
архивируются, low-signal отбрасываются, при повторном появлении ключа — lazy-restore.
**Исключение:** отпечатки, присутствующие в каталоге блок-листа, освобождены от
архивации — иначе молчащая enforced-запись выпала бы из проверки auto-demote (она
читает только активный аккумулятор), и снятие по неактивности перестало бы
срабатывать именно для тех записей, ради которых существует.

## 12. Доставка и SLA

merge PR → каталог раздается на эдж в фоне → эдж подхватывает. Эдж работает на
последней доставленной копии (fail-stale), запрос клиента доставки никогда не ждет.

| Метрика | Значение | Что включает |
| --- | --- | --- |
| отчет → прод-блокировка | **≤4ч** | наблюдение staging + ревью + активация + доставка |
| merge → каталог на эдже | ≤15 мин | доставка каталога |
| минимальное наблюдение staging | ≥48ч | окно подтверждения перед активацией |
| TTL auto-demote | ~2 недели | порог неактивности |

## 13. Наблюдаемость и аудит

- **Ежедневный отчет** — ранжированные HIGH/MEDIUM/LOW кандидаты с evidence-chain,
  отправляется ответственному.
- **`staging_match`** — observe-only счетчик: сколько раз staged-запись сматчилась,
  не блокируя. Наземная правда для перехода `staging → active`.
- **Паспорт записи** — в PR и в комментарии над записью каталога: action, причина,
  score/тир, evidence chain, пройденные гейты, human_share, дата ревизии, план
  жизненного цикла. По любой enforced-записи видно, почему и на каком основании она
  там.

## 14. Робастность скоринга (anti-poisoning)

Петля частично автоматическая (draft-PR на HIGH) → ее можно атаковать.
Злоумышленник может водить «человеческий» трафик под целевым отпечатком, чтобы
поднять human_share и **защитить** свой отпечаток от блока (или **загрязнить**
чужой, чтобы спровоцировать ложный блок). Контракт устойчивости:

- **Взвешенный human_share.** Доля genuine-browser событий считается не наивно: события
  взвешиваются так, чтобы инъекция из узкого набора источников не могла дешево
  поднять долю (диверсификация источников событий).
- **Known-good инвариант.** Отпечаток, совпавший с позитивным каталогом браузеров
  (§8), **никогда** не авто-блокируется — нельзя подставить под блок настоящий
  Chrome/Firefox.
- **Snapshot-diff цепочки доказательств.** Evidence-chain кандидата сравнивается во
  времени: резкий «человеческий» сдвиг под HIGH-отпечатком — сам по себе сигнал
  манипуляции, а не основание снять подозрение.

Высокий порог промоута и человек-в-петле — последняя линия: ложный блок дорог,
поэтому решение обратимо и проходит ревью.

## 15. Технические гарантии и ограничения

- **Слой никогда не на горячем пути.** Его недоступность не влияет на латентность,
  доступность и решения каскада (fail-stale).
- **Ни одно изменение enforcement не происходит без человека.** Автомат готовит
  draft-PR; merge — ручной.
- **Все обратимо.** Любой переход откатывается адресно или целиком, в рамках SLA
  доставки.
- **Блокировка только после наблюдения.** Между прогнозом и enforcement всегда есть
  observe-only фаза на живом трафике.
- **Чего слой НЕ делает (намеренно):** не блокирует общие отпечатки инструментов
  (intent-правило) — это адресная работа по UA/IP, решает человек; не вводит
  enforced-TTL на эдже (контракт каталога не меняется); записи без истории
  наблюдения автомат не снимает.

## 16. Зоны ответственности

| Кто | Что делает |
| --- | --- |
| **Аналитический воркер** | читает поток вердиктов, считает score/гейты, пишет артефакты, шлет отчет |
| **Автомат** | готовит один draft-PR за прогон в обе стороны; никогда не мержит |
| **Оператор (человек)** | ревьюит и мержит PR; адресно promote/demote; решает кейсы intent=false |
| **Каскад (эдж)** | исполняет доставленный каталог; эмитит поток вердиктов; матчит staging в observe-only |

## 17. Что не входит

- UI для просмотра кандидатов и аналитики клиентом.
- Enforced-TTL и любые изменения контракта каталога/каскада.
- Поведенческий ML на полных сессиях с клиентским биконом — это другой слой/продукт.
- DDoS, WAF, API-защита — соседние слои со своими спецификациями.
