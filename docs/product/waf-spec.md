# WAF — контентная инспекция L7 — спецификация (серия W)

**Версия:** v0.1 · **Статус:** проектный контракт (целевое поведение) · **Дата:** 2026-05-31

Документ описывает целевое поведение WAF-оси — в том же смысле, в каком
[vision.md](vision.md) описывает каскад. Что уже в стенде, а что нет — сверяй с
[PROGRESS.md](../../PROGRESS.md) и кодом. Выбор движка (build-vs-buy) — открытый вопрос,
решается спайком и ADR-007 (см. §4); до ADR в код не коммитимся.

**Сопутствующие материалы (как у vision):**
[waf-rules-reference.md](waf-rules-reference.md) — правила/сигнатуры в формате «если условие

## 1. Что это

Слой контентной инспекции HTTP-запроса на сигнатуры атак (негативная модель
безопасности): SQL-инъекции, XSS, path-traversal, command-injection, очевидный SSRF/LFI,
плюс virtual patching — точечные правила-щиты под конкретные CVE/эндпоинты клиента.

WAF — это негативная модель (ищем известные плохие паттерны). Её комплемент —
позитивная модель контракта API (что РАЗРЕШЕНО), см.
[api-contract-governance-spec.md](api-contract-governance-spec.md). Границу двух моделей
фиксируем в ADR-007.

## 2. Зачем

В каскаде сегодня нет инспекции тела запроса, query/POST-параметров и заголовков на
сигнатуры. [vision.md](vision.md) называет DDoS явной целью, а WAF — лишь косвенно (XSS как
причина `HttpOnly` на cookie). Это **зелёное поле**: целый класс атак уровня приложения
(OWASP Top-10 ядро) сейчас проходит каскад насквозь к origin.

## 3. Где в каскаде

WAF добавляет **новую стадию инспекции контента** (`waf`), которая копит флаги
(`waf:sqli`, `waf:xss`, …) и на критичных правилах способна сама блокировать — по аналогии
с тем, как `tls_fp_blocklist` hit делает прямой `policy.enforce(403)`.

```
hygiene → [contract (Q)] → reputation → tls_fp → [WAF inspection] → rate_limits → verification
```

Сохраняется инвариант [rules-reference.md](rules-reference.md): **единственная точка
консолидации флагов — L5** (`verification`), правила не выдают вердикт сами, кроме явных
hard-block exit-точек под `policy.enforce`. WAF встаёт после дешёвых identity-проверок и
позитивного контракта (Q), до дорогих поведенческих (rate_limits) — точное место
фиксируется при реализации.

## 4. Развилка движка — спайк + ADR-007 (решение отложено)

WAF-движок намеренно оставлен как ADR-кандидат: build-vs-buy не решён.

**Вариант A — [Coraza](https://github.com/corazawaf/coraza) + OWASP CRS.** Go-реализация
ModSecurity seclang + проверенный годами Core Rule Set.
- **+** мгновенный охват Top-10, поддерживаемые правила, знакомый seclang.
- **−** чужая модель правил вне нашего Channel C / shadow-mode / `bac_log`; либо Go-сервис
  (лишний `auth_request`-хоп, отвергнут в ADR-001 в пользу edge-Lua), либо незрелый
  Lua-биндинг; латентность инспекции тела — нужен замер; CRS ложняки требуют тюнинга, не
  ложащегося в наш staging→active «из коробки».

**Вариант B — свой ruleset в стиле каскада.** Стадия `waf.lua` со своими сигнатурами;
каталог `waf_rules` через Channel C ровно как `tls_fp_blocklist`; shadow/active через
`policy.enforce`; флаги в `bac_log`; staged rollout и `git revert` бесплатно (ADR-006).
- **+** единая архитектура (лог/метрики/kill-switch/mode-gate/PR-воркфлоу/CI-валидация),
  управляемая латентность.
- **−** сами отвечаем за полноту и анти-evasion; медленный набор охвата; риск «свой CRS хуже CRS».

**Вариант C — гибрид:** свой движок исполнения + импорт подмножества CRS-сигнатур как
данных в наш каталожный формат.

**Рекомендация — спайк перед коммитом** (по образцу `infra/nginx-lua-poc/spikes/`, ADR-002):
(1) замерить per-request латентность инспекции тела Coraza vs нативной Lua на репрезентативном
теле; (2) оценить, ложится ли CRS-тюнинг в shadow→staging→active; (3) прикинуть объём своего
сигнатурного ядра под Top-10; (4) зафиксировать границу Q↔W. Результат — **ADR-007 «WAF-движок:
build vs buy»**.

## 5. Как — компоненты

### 5.1 Скоуп MVP
- Инспекция **query-string и POST-тела** (form-urlencoded + JSON; multipart — фаза 2).
- Инспекция **заголовков и пути** (path-traversal, нулевые байты, протокольные аномалии).
- Сигнатуры под **OWASP Top-10 ядро**: SQLi, XSS, path-traversal, command-injection, SSRF/LFI.
- shadow по умолчанию (как весь каскад) + per-host on/off через policy.

Вне MVP: ML-аномалии тела, CRS paranoia 3+, полная анти-evasion нормализация всех кодировок.

### 5.2 Движок инспекции
Стадия `waf.lua` по выбранному в ADR пути: пре-процессор нормализации + матч сигнатур;
флаги в `bac_log`; критичные правила → `policy.enforce`. Метрики
`antibot_rule_total{stage="waf",...}`.

### 5.3 Сигнатурный каталог `waf_rules`
Доставка через Channel C как `tls_fp_blocklist`: git — единственный источник истины (ADR-006),
PR-only + CODEOWNERS, staged rollout (staging→active, `staging_match` в логе), `git revert`.
Формат правил определяется ADR-007. CI-валидация (синтаксис/компиляция) перед мержем.

### 5.4 Per-host WAF-профиль
Расширение policy: `waf_enabled`, `waf_paranoia` (уровень), `waf_disabled_rules` (массив id
выключенных правил — для ложняков конкретного клиента). B10 Policy API (PATCH). mode/strictness
независимы от профиля.

### 5.5 Virtual patching
Точечное правило-щит под конкретную CVE/эндпоинт клиента — технически запись в `waf_rules` с
быстрым PR-воркфлоу (как HIGH-кандидат blocklist → PR в `tls_fp_blocklist`). Runbook быстрого
выката: PR → staging (наблюдение) → active; быстрый revert. Закрывает дыру на эдже за минуты,
пока origin патчат.

## 6. Открытые вопросы
- **Буферизация тела** (`lua_need_request_body`/`request_body`) конфликтует с большими
  аплоадами → лимит размера (см. resource limits в Q-спеке) + bypass для media/upload.
- **Нормализация** (URL-decode, unicode, comment-strip) — общий пре-процессор ПЕРЕД
  сигнатурами, иначе тривиальный evasion.
- **Латентность** инспекции тела на каждом запросе — замер в спайке (§4).

## 7. Что переиспользуем
ADR-006 (git-каталоги), B10 (Policy API), `policy.enforce` (mode-gate / shadow→active),
`bac_log`/метрики, kill-switch (A12), staged rollout (A11), паттерн promotion (`tls_fp_blocklist`),
CI-контракт каталогов (B13).

## 8. Честные границы
- WAF (негативная модель) **не заменяет** позитивный контракт API (Q) — это разные модели,
  применяются вместе.
- До ADR-007 движок не выбран → код не коммитим (статус-инвариант).
- Полнота сигнатур и анти-evasion — длинный хвост, добивается итеративно (особенно в варианте B).
