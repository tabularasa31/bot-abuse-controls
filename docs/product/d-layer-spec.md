# Слой D — аналитика, скоринг и жизненный цикл блок-листа

> **Статус документа: behavioral contract (спека «до продукта»).** Как и
> [vision.md](vision.md) был написан до того, как появился каскад, этот документ
> описывает **целевое поведение** всей плоскости D целиком — чтобы по нему можно
> было взять и построить продукт. Часть слоя уже работает на стенде (D1, см.
> [Roadmap слоя D](#roadmap-слоя-d) и [PROGRESS.md](../../PROGRESS.md)), часть —
> контракт на будущее. Где поведение уже реализовано — это отмечено; где нет —
> описано как требование к реализации, а не как факт.
>
> Это **не** инструкция по деплою на боевой prod-edge. Для нашей работы «реализовать»
> = «реализовать в инструментах стенда» (`infra/demo-stand/scripts/`,
> `infra/demo-backend/`, `scripts/`), ровно как каскад живет в
> `infra/demo-stand/lua/`.

## Обзор слоя

### Что это

Каскад ([vision.md](vision.md), слои L1–L6) — это **горячий путь**: он принимает
решение по каждому запросу за микросекунды, опираясь на каталоги, уже лежащие в
памяти proxy. Каскад ничего не «придумывает» сам — он исполняет каталоги.

**Слой D — это контур, который эти каталоги наполняет и поддерживает в актуальном
состоянии.** Он работает в фоне, оффлайн, на backend-стороне, и замыкает петлю:

```
        ┌──────────────────────── петля слоя D ────────────────────────┐
        │                                                              │
   эдж (каскад) ──BAC_LOG──► Loki ──► аналитика ──► скоринг ──► решение │
        ▲                                                          │   │
        │                                                          ▼   │
        └──── Channel C ◄──── каталог (PR) ◄──── автомат / человек ◄────┘
```

Эдж пишет структурный лог каждого вердикта. Лог стекается в Loki. Слой D читает
Loki, строит per-fingerprint картину, **ранжирует** подозрительные TLS-отпечатки,
**решает** (через гейты-вето), какие из них безопасно блокировать, проводит их по
**жизненному циклу** (staging → наблюдение → active → снятие), и **доставляет**
результат обратно на эдж через каталог `tls_fp_blocklist` (Channel C, PR-only по
[ADR-006](../architecture-decisions/006-slow-catalogs-as-files.md)).

То есть слой D — это **обучающая обратная связь** продукта: каскад порождает
наблюдения, слой D превращает наблюдения в конфигурацию каскада.

### Из чего состоит

| Компонент | Что делает | Где живет | Статус |
| --- | --- | --- | --- |
| **Producer / аналитика** | читает Loki, строит per-fp view, считает score+gates, пишет артефакты, шлет утренний отчет | backend+obs VM, контейнер `antibot-analytics` | ЕСТЬ (D1) |
| **Модель скоринга** | аддитивный score (ранжирование) + гейты-вето (допуск) + intent-правило | `infra/demo-stand/scripts/analyze.py` | ЕСТЬ (D1) |
| **Жизненный цикл** | candidate → staging → наблюдение → active → auto-demote → remove | `scripts/promote-fp.sh` / `demote-fp.sh` | ЕСТЬ (D1) |
| **Автомат (autopilot)** | из артефактов собирает **один draft-PR в сутки** в обе стороны | `scripts/blocklist-autopilot.sh` | ЕСТЬ (D1) |
| **Состояние** | аккумулятор lifetime-сигналов (`seen-fps.json`) + его ротация | `state/`, `rotate-state.py` | ЕСТЬ (D7 — ротация) |
| **Доставка** | merge PR → Channel C → эдж (≤15 мин) | backend catalog-server | ЕСТЬ |
| **Positive-каталоги** | известные браузерные fp, headless-профили — снижают ложняк | `tls_fp_browser_profiles`, D2/D4 | ПЛАНИРУЕТСЯ |
| **Регрессия / харнесс** | adversarial-корпус, integration-тесты, weekly run | D8/D9 | ПЛАНИРУЕТСЯ |

### Чем НЕ является

- **Не hot-path.** Слой D никогда не вызывается в обработке запроса. Падение
  аналитики, Loki или автомата не влияет на латентность и доступность каскада —
  эдж работает на последней доехавшей копии каталога (fail-stale).
- **Не enforcement.** Слой D не блокирует трафик сам. Он только редактирует
  каталог; блокирует — каскад, по доехавшему каталогу.
- **Не ML.** Это детерминированный скоринг по объяснимым сигналам с жесткими
  гейтами, не модель. Каждое решение разворачивается в человекочитаемый паспорт.
- **Не автономен в проде.** Автомат **никогда не мержит** и никогда не открывает
  не-draft PR. Финальное «да» дает человек через ревью PR. Слой D готовит
  решение, человек его подтверждает.

### Принцип в одном экране

- **Эдж — producer наблюдений, слой D — consumer.** Граница — Loki. Все, что
  слою D нужно знать о реальности, он берет из лога, а не из живого трафика.
- **Score только ранжирует. Допуск решают гейты.** Это центральная развязка
  (см. [Модель скоринга](#модель-скоринга)). Высокий score сам по себе не
  блокирует ничего; низкий — не мешает попасть в письмо для человека.
- **Наблюдение важнее прогноза.** Прежде чем что-то блокировать, мы это
  наблюдаем в observe-only режиме (`staging`) на живом трафике и блокируем
  только по факту чистого наблюдения, а не по исходному прогнозу.
- **Снятие так же автоматизировано, как и постановка.** Человек не способен
  отследить, какой из десятков fp перестал быть угрозой; это делает автомат по
  неактивности, в обе стороны, тоже через draft-PR.
- **Каждое изменение каталога — через PR с аудит-паспортом.** Никакого
  прямого SQL/admin-UI к блок-листу: причина, evidence, гейты и lifecycle-план
  фиксируются в теле PR и в `#`-комментарии каталога.

## Источник данных — Loki

### Контракт лога

Эдж на каждом обработанном запросе эмитит одну строку `BAC_LOG {json}`
(`infra/demo-stand/lua/bac_log.lua`). Это **единственный** вход слоя D: вся
картина строится из этого потока, отдельной телеметрии слой D не заводит.

Поля, на которые опирается слой D (контракт — стабильны между итерациями, как и
stage-коды каскада):

| Поле | Смысл для слоя D |
| --- | --- |
| `tls_fp` | ключ всего анализа; per-fp агрегация идет по нему |
| `ip` | `n_ips`, multi-IP сигнал, проверка против `ip_whitelist` |
| `ua` | automation-UA / impersonator / genuine-browser классификация |
| `path` | recon-URI сигнал (`/.env`, `/wp-login`, …) |
| `verdict` | identity-allow детект (любой `verdict=allow` → allowlist-вето) |
| `rule` | какое правило сработало (для атрибуции) |
| `staging_match` | `["tls_fp_blocklist:<fp>"]` — observe-only матч staging-записи |
| `asn` / `asn_type` | DC-ASN сигнал |
| time | окно наблюдения, `days_seen`, persistence |

### Почему Loki, а не эдж

Исторически аналитика жила на эдж-VM и читала `docker logs nginx-demo` — сырье
~24 часа. Этого мало: наблюдение staging требует 48 часов, auto-demote — 14 дней.
К тому же аналитика на хот-пас-проксе архитектурно неуместна.

Решение: **аналитика переехала на backend+obs VM, источник — Loki** (ретенция
7 дней, централизованно, in-network). Это:

- закрывает проблему ретенции для staging-окна (48ч < 7д);
- кладет аналитику на ее естественную плоскость (backend, не proxy);
- дает единый источник по всему пулу эджей, а не по одному контейнеру.

**Ограничение Loki, заложенное в дизайн.** Loki read API наружу не открыт
(только Grafana in-network `http://loki:3100`; `auth_enabled: false`). Значит
читать Loki может **только сервис внутри сети backend** — отсюда producer/consumer
разделение: добыча данных (нужен in-network Loki) отделена от git/gh (нужен
чекаут + `gh`, хост-уровень). Полная BAC_LOG-строка доезжает в тело записи Loki
(promtail кладет сырой JSON payload), `tls_fp/ip/ua/path/staging_match` достаются
через `| json` — ничего не теряется, Loki полноценный источник.

**Ретенция 7д < TTL auto-demote 14д** — поэтому нужен персистентный аккумулятор
`seen-fps.json` (см. [Состояние](#состояние-и-его-ротация)): `last_seen` за
горизонтом Loki берется из него.

### Режим отладки

`analyze.py --source docker` остается как локальный debug-инструмент (читает
`docker logs nginx-demo` на эдже). Боевой источник — `--source loki` (default).
Скоринг и рендер от источника не зависят: оба режима скармливают сырые
`BAC_LOG {json}` тела в общий `_event_from_bac_line`.

## Что такое отпечаток (fp)

Любой клиент при HTTPS-рукопожатии шлет TLS ClientHello: список шифров,
расширения, версии — в определенном порядке. Это «почерк», который эдж
сворачивает в строку-отпечаток (`infra/demo-stand/lua/ja4_compute.lua`):

```
L<ver><sni><cipher_cnt><alpn>_<hash_b>_<hash_c>
```

Ключевое свойство для слоя D: **внутри одного fp `cipher_count` и хеши
фиксированы** — это часть токена. Реальные браузеры (Chrome/Firefox/Safari)
предлагают число шифров из набора `{15, 16, 20}`; инструменты-автоматизаторы
(curl/python/go) — другое. Это эмпирика стенда и основа purity-вето: расхождение
между «UA говорит браузер» и «почерк не браузерный» = маскировка.

## Модель скоринга

Это ядро слоя D. Решение «блокировать ли fp» состоит из **двух независимых
слоев**, которые нельзя смешивать.

### Слой 1: score — ранжирование (аддитивно)

**Score отвечает на вопрос «насколько это похоже на бота».** Аддитивная сумма
сигналов, нужна только чтобы отсортировать кандидатов в утреннем письме. Сама по
себе **ничего не блокирует.**

| Сигнал | Очки | Смысл |
| --- | --- | --- |
| impersonator | **+3** | браузерный UA на fp известного инструмента (маскировка) |
| suspicious cipher | +1 | `cipher_count ∉ {15,16,20}` при браузерном UA |
| automation UA | +1 | UA сам по себе бот (curl/python/go/okhttp/bot/scanner) |
| DC ASN | +1 | хотя бы один IP в hosting-ASN |
| multi-IP | +1 | ≥2 разных IP под одним fp |
| persistent | +1 | fp виден ≥2 разных дней |
| recon URI | +1 | обращения к `/admin`, `/.env`, `/wp-login`, … |

Тиры: **HIGH ≥5 · MEDIUM 3–4 · LOW 1–2.**

> `suspicious` весит +1 (не больше) намеренно: слабая эвристика, ложащаяся на
> нетипичных, но легитимных браузерах. `impersonator` (+3) опирается на словарь
> известных инструментов — высокая точность, поэтому вес выше.

### Слой 2: gates — допуск (вето, не складываются)

**Gates отвечают на вопрос «безопасно ли это блокировать».** Это пороги-вето:
score может быть сколь угодно высоким — если хоть один gate не пройден, промоута
нет. Гейты НЕ суммируются и НЕ компенсируют друг друга.

| Gate | Условие | Зачем |
| --- | --- | --- |
| **purity** (вето) | `human_share ≤ 0.05` | под fp не ходят живые люди |
| **volume** | `n_events_lifetime ≥ 20` и `n_ips ≥ 1` | отсечь шум на единичных запросах |
| **allowlist/verified** (вето) | ни одного `verdict=allow` под fp, ни один IP не в `ip_whitelist` | не блокировать легитимный/verified-трафик |
| **dedup** | fp еще нет в каталоге | идемпотентность |
| **intent** | `impersonator OR (recon AND NOT generic_honest_tool)` | не блокировать общий fp инструмента (см. ниже) |

### Два разных риска ложного блока

Это ключ ко всему дизайну. Заблокировать fp по ошибке можно **двумя разными
способами**, и закрываются они **разными механизмами** — поэтому purity и intent
существуют отдельно, а не сливаются в один порог.

#### Риск 1: «неизвестный легитимный браузер приняли за бота» → purity-вето

Считаем долю событий fp, которые выглядят как **настоящий браузер**.
Событие = *genuine browser*, если **одновременно**:

1. UA говорит браузер (Chrome / Firefox / Safari);
2. число шифров браузерное (`cipher_count ∈ {15,16,20}`);
3. хеши fp **не** из словаря инструментов.

`human_share = genuine_browser_events / total_events`. Гейт **purity**:
`human_share ≤ 0.05` (флаг `--max-human-share`). Превышен — блокировать нельзя
при любом score: под этим fp ходят живые люди.

Почему три условия вместе: UA подделать легко (бот пишет «я Chrome»), «почерк»
рукопожатия — труднее. Верим, что это человек, только когда UA браузерный И
почерк браузерный И это не опознанный инструмент. Если UA = Chrome, а почерк =
curl (пункты 1 и 2 расходятся) — это **маскировка**, и она НЕ считается человеком
(наоборот, это impersonator-сигнал +3).

#### Риск 2: «заблокировали общий отпечаток инструмента» → intent-правило

Отпечаток самого `curl` (или python-requests) **общий для всех его пользователей
в мире**: мониторинги, CI/CD, healthcheck'и, легитимные API-клиенты. recon-URI от
одного актора **не делает общий fp безопасным для блокировки** — и purity тут не
спасает: браузерных событий под curl нет, `human_share = 0`, purity пройден.
Заблокировать fp curl = отрезать всю легитимную автоматизацию мира, использующую
curl.

Поэтому авто-блок fp оправдан только при **намерении, специфичном для самого fp**:

- **impersonator** — браузерный UA на инструментальном fp. Сочетание само по
  себе аномально: настоящий пользователь так не делает. Отпечаток такого
  «притворщика» специфичен — блокировать безопасно.
- **recon на не-generic fp** — recon-URI под отпечатком, который **не** является
  известным honest-инструментом
  (`generic_honest_tool = известный_инструмент И НЕ impersonator`). Неизвестный
  сканерный fp с recon — специфичная сигнатура, блок безопасен.

```
intent = impersonator OR (recon AND NOT generic_honest_tool)
```

Честный curl с recon → `intent = false` → автомат его не трогает. Это кейс для
`ua_blacklist` / `ip_blocklist` (адресно по UA или IP, а не по общему fp), и его
решает человек.

### auto_eligible — триггер автомата

```
auto_eligible = tier == HIGH
              AND days_seen ≥ MIN_DAYS_PROMOTE
              AND все gates пройдены
              AND intent
```

Только записи с `auto_eligible` автомат предлагает в один draft-PR на `staging`.
Все остальное (HIGH без intent, MEDIUM, LOW) остается в утреннем письме на
усмотрение человека.

> **Почему `MIN_DAYS_PROMOTE` низкий (1).** `staging` — observe-only (матчит, не
> блокирует), поэтому проверять «устойчивость» fp ДО входа в staging смысла мало:
> настоящий полигон — это 48-часовое окно `staging → active`, а блипы-однодневки
> отсекает volume-гейт (`MIN_EVENTS`). Вход в staging дешевый и быстрый, вся
> строгость — на активации.

## Жизненный цикл записи блок-листа

Каждый fp проходит управляемый путь от кандидата в письме до enforcement и
обратно. Ни один переход не блокирует трафик «вслепую» — между прогнозом и
блокировкой всегда есть фаза наблюдения на живом трафике.

```
   кандидат в письме
        │ promote (прогноз: HIGH + gates + intent)
        ▼
     staging ──набл. ≥48ч, FP=0, ≥10 матчей──► activate (подтверждено) ──► active
        │ задел живой браузер → флаг demote/remove                          │ молчит >14д
        └──────────────────────────────────────◄────────────────────────────┘
                                  auto-demote: active → staging → remove
```

### Состояния каталога

`catalogs/tls_fp_blocklist.yaml` хранит per-fp статус ∈ `{staging, active}`
(strict yaml.v3, валидируется `validate-catalogs`). Над каждой записью —
`#`-комментарий-паспорт (причина, score, evidence, human_share, review-by).

| Статус на эдже | Поведение каскада |
| --- | --- |
| `staging` | **match-but-observe**: эдж матчит fp, пишет `staging_match`, **НЕ блокирует** (не 403) |
| `active` | **enforce**: `verdict=block, rule=tls_fp_blocklist` (403) |
| (нет записи) | каскад fp не знает |

### Переход 1: candidate → staging (promote)

Триггер — прогноз: HIGH + все gates + intent. `promote-fp.sh <fp> --reason "..."`
открывает PR со статусом `staging`. Гейты тут — жесткие вето (purity/allowlist
не перебиваются). После merge запись доезжает на эдж (Channel C, ≤15 мин) и
начинает матчиться в observe-only.

Зачем staging-фаза: дает **наземную правду о ложняках до enforcement**. Мы видим,
кого бы заблокировали, не блокируя.

### Переход 2: staging → active (activate)

Триггер — **подтверждение наблюдением**, не исходный прогноз. По событиям с
`staging_match ⊇ tls_fp_blocklist:<fp>` за окно наблюдения:

| Гейт | Условие | Зачем |
| --- | --- | --- |
| окно | в staging ≥ `MIN_STAGING_HOURS` (48ч) | застать разный суточный трафик |
| объем | ≥ `MIN_STAGING_MATCHES` (10 матчей) | иначе судить не о чем |
| ноль ложняков (вето) | `human_share` среди матчей = 0 | задел живой браузер → НЕ активировать |
| allowlist re-check | среди матчей нет whitelist/verified | перепроверка на реальном трафике |

Вердикты `find_staging_observation`:

- **`activate`** — все ок → `promote-fp.sh <fp> --activate` открывает PR-2
  (`staging → active`). После merge эдж начинает блокировать.
- **`fp_caught`** — наблюдение поймало легитимный трафик → активацию НЕ
  предлагаем, запись — кандидат на `demote --remove`.
- **`observe`** — мало матчей / мало времени → наблюдаем дальше.

### Переход 3: auto-demote (снятие по неактивности)

Человек не отследит, какой fp перестал быть угрозой, поэтому это делает автомат.
«Последний раз виден» = `max(days_seen)` из аккумулятора `seen-fps.json` (живет
дольше 7д Loki-ретенции). Если `days_silent > TTL_DAYS` (14) — кандидат на
снятие. **Двухступенчато:**

1. `active → staging` (молчит >14д) — снимаем enforcement, оставляем наблюдение;
2. `staging → remove` (снова молчит >14д) — удаляем совсем.

Обе ступени — draft-PR. Записи **без истории наблюдения** (`unknown`, никогда не
матчились) автомат **не трогает** — оставляет человеку.

> **TTL здесь — НЕ enforced-протухание на эдже** (поля TTL в каталоге нет, контракт
> каталога слой D не меняет), а порог неактивности для авто-детектора снятия.

### Ручное снятие (обратимо)

```sh
scripts/demote-fp.sh <fp> --reason "false-positive: легит-клиент с тем же fp"   # active → staging
scripts/demote-fp.sh <fp> --reason "campaign over" --remove                      # удалить
```

Полный откат любого PR — `git revert` (см.
[catalog-rollback.md](../runbooks/catalog-rollback.md)). Оба пути в рамках SLA
≤15 мин на доставку.

## Автоматизация (autopilot)

`blocklist-autopilot.sh` — cron-драйвер, превращающий суточные артефакты в
**ОДИН draft-PR за прогон**. Контракт автомата:

- **Никогда не мержит. Никогда не открывает не-draft PR.** Человек ревьюит и
  мержит. Автомат только готовит решение.
- **Двунаправлен.** В одном PR собирает все созревшее за прогон:
  - auto-promote HIGH (`auto_eligible`) → `staging`;
  - activate staging-записей с `verdict == activate`;
  - auto-demote молчащих >14д (`active→staging`, `staging→remove`).
- **Один PR в сутки.** Ветка `blocklist-auto-YYYY-MM-DD`, все изменения батчатся.
  Раньше автомат открывал отдельный PR на каждый fp — это шумно; теперь одна
  ветка/PR на прогон.
- **Идемпотентен.** Гейт — наличие **открытого** PR для сегодняшней ветки
  (`gh pr list --head`), не просто запушенной ветки (push и pr-create — разные
  шаги, push без PR не должен заблокировать день). Стейл-ветку (локальную и на
  origin) автомат чистит перед повтором.
- **Freshness guard.** Каждый артефакт несет `generated_utc`. Если
  `candidates.json` старше `BAC_ARTIFACT_MAX_AGE_HOURS` (26ч) — аналитика, видимо,
  лежит; автомат **не действует на устаревших данных** и выходит no-op.
- **Чистая рабочая копия при любом исходе.** EXIT-trap откатывает правки каталога
  и возвращает на базовую ветку, даже если apply прервался на середине.

PR-тело — паспорт по секциям (Promote → staging / Activate → active / Demote),
каждая строка с score, tier, evidence, human_share, review-by.

### CI на catalog-only PR

PR от автомата меняет только `catalogs/` → CI гоняет **только**
`validate-catalogs`. Это сделано path-фильтром в `.github/workflows/ci.yml`: job
`changes` ставит `code=true` только если изменилось что-то кроме
`catalogs/`/`docs/`/`*.md`; тяжелые джобы (test/lint-lua/lint-go/test-go/
lint-shell/smoke/integration) гейтятся `if: needs.changes.outputs.code == 'true'`;
`validate-catalogs` запускается всегда. Это держит автоматические PR быстрыми и
дешевыми.

## Артефакты и контракт данных

Producer (`analyze.py` в контейнере `antibot-analytics`) на каждом прогоне пишет
в `state/` набор JSON-вьюх. Consumer'ы (`promote-fp.sh`, `autopilot.sh`) читают
**только** эти артефакты — Loki им напрямую не нужен.

| Артефакт | Команда | Содержит |
| --- | --- | --- |
| `candidates.json` | `--candidates-json` | `high/medium/low[]`: fp, score, tier, reasons, `human_share`, gates{}, `auto_eligible` |
| `staging-observation.json` | `--staging-observation-json` | `observations[]`: fp, n_matches, observed_hours, human_share, verdict (`activate`/`observe`/`fp_caught`) |
| `stale.json` | `--stale-blocklist-json --ttl-days N` | `stale[]`: fp, status, days_silent, stale(bool), unknown(bool) |
| `report.html` | `--html` | утреннее письмо |
| (subject) | `--subject` | одна строка для Subject |

Каждый артефакт несет `generated_utc` (для freshness guard). Все они и `seen-fps.json`
живут под `state/` (gitignored), на backend-VM.

## Состояние и его ротация

### Аккумулятор `seen-fps.json`

С Loki-источником большинство сигналов (`days_seen ≤7д`, persistence, multi-IP)
берутся из Loki напрямую. Персистентный аккумулятор нужен ровно для того, что
Loki за 7 дней не помнит:

- `n_events_lifetime` (volume-гейт смотрит на накопленный объем);
- `last_seen` для auto-demote (TTL 14д > 7д ретенции Loki).

Ключ — `fp`. Аккумулятор обновляется на каждом прогоне аналитики.

### Ротация (D7)

`seen-fps.json` и `ip-cache.json` растут неограниченно. `rotate-state.py`
ограничивает рост: старые записи архивируются в `state/archive/`. Ротация —
non-fatal (ее сбой не блокирует утренний отчет) и идет **до** `analyze.py` в
суточном прогоне.

> **Важное исключение.** fp, присутствующие в каталоге блок-листа,
> **освобождены** от архивации/дропа при ротации. Иначе молчащий enforced-fp
> уехал бы в архив и выпал из проверки auto-demote (она читает только активный
> `seen-fps.json`) — и снятие по неактивности перестало бы срабатывать именно для
> тех записей, ради которых оно существует. Детали TTL-логики и env-ручек —
> [`infra/demo-stand/scripts/README.md`](../../infra/demo-stand/scripts/README.md).

## Доставка, расписание и SLA

### Доставка на эдж

merge PR в `main` → backend catalog-server раздает обновленный
`tls_fp_blocklist` → эдж подхватывает в фоне. SLA доставки PR-каталогов —
**≤15 минут** (см. [vision.md](vision.md), двухканальная конфигурация, Channel C).
Эдж работает на последней доехавшей копии (fail-stale), запрос клиента backend
никогда не ждет.

### Расписание (cron на backend-VM)

Аналитика — **cron-driven one-shot** (контейнер не крутит loop): host-cron делает
один прогон в сутки. Порядок: `rotate-state.py` (D7) → `analyze.py` (артефакты +
отчет) → autopilot читает свежие артефакты.

```cron
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
# 05:00 UTC = 08:00 MSK — прогон аналитики (Loki → state/*.json + email)
0 5 * * * cd /home/ubuntu/abuse-controls/infra/demo-backend && /usr/bin/docker compose -f docker-compose.backend.yml --profile observability run -T --rm analytics >> /home/ubuntu/analytics-cron.log 2>&1
# 05:30 UTC = 08:30 MSK — autopilot: один draft-PR по свежим артефактам
30 5 * * * cd /home/ubuntu/abuse-controls && ./scripts/blocklist-autopilot.sh >> /home/ubuntu/autopilot.log 2>&1
```

> **Время — в явном UTC.** Хост в UTC, а Debian-cron `CRON_TZ` **не уважает**
> (проверено: `0 8` с `CRON_TZ=Europe/Moscow` все равно сработал в 08:00 UTC).
> Поэтому `05:00 UTC = 08:00 MSK` (Москва круглый год без DST). `-T` — cron не
> выделяет TTY; `PATH` — чтобы cron нашел `git`/`gh` для autopilot.

> **Деплой-нюанс.** Авто-деплой (`update.sh`) делает `up -d --build` **без**
> `--profile observability` → сервисы analytics/loki/grafana этим деплоем **не
> пересобираются**. После правки образа аналитики его пересобирают вручную:
> `docker compose -f docker-compose.backend.yml --profile observability build
> analytics`. Сам `analyze.py` bind-монтируется в контейнер (не запекается в
> образ), поэтому изменения кода применяются на следующем прогоне после merge+pull
> без пересборки.

### SLA жизненного цикла

| Метрика | Значение | Что включает |
| --- | --- | --- |
| Письмо → прод-блокировка | **≤4ч** | staging-наблюдение + два ревью + активация + доставка |
| merge → каталог на эдже | ≤15 мин | Channel C |
| Минимальное staging-наблюдение | 48ч | окно подтверждения перед активацией |
| Auto-demote TTL | 14д | порог неактивности |

## Наблюдаемость и аудит

- **Утренний отчет** (08:00 MSK) — ранжированные HIGH/MEDIUM/LOW кандидаты с
  evidence-chain, отправляется почтой (msmtp, креды из env `MSMTP_*`/`REPORT_*`).
- **`staging_match`** — observe-only метрика на эдже
  (`antibot_staging_match_total`): сколько раз staging-запись сматчилась, не
  блокируя. Это наземная правда для перехода staging → active.
- **PR-паспорт** — каждое изменение каталога несет в теле PR и в `#`-комментарии
  каталога: action, reason, score/tier, evidence chain, пройденные гейты,
  human_share, events, review-by, lifecycle/rollback-план. Это аудит-след: по
  любой enforced-записи видно, почему и на каком основании она там.
- **`/__admin` на эдже** — показывает текущий загруженный блок-лист и статус
  каждой записи (staging:block / active:block) — для проверки доставки.

## Константы и ручки

| Константа | Дефолт | Флаг | Смысл |
| --- | --- | --- | --- |
| `MAX_HUMAN_SHARE` | 0.05 | `--max-human-share` | purity-вето |
| `MIN_EVENTS` | 20 | `--min-events` | volume-гейт |
| `MIN_DAYS_PROMOTE` | 1 | `--min-days-promote` | дней до входа в staging |
| `MIN_STAGING_HOURS` | 48 | `--min-staging-hours` | окно наблюдения |
| `MIN_STAGING_MATCHES` | 10 | `--min-staging-matches` | объем наблюдения |
| `TTL_DAYS` | 14 | `--ttl-days` | порог неактивности auto-demote |

`--force` (промоут без evidence/наблюдения — для демо), `--dry-run` (показать
diff+PR-тело и стоп).

## Гарантии и ограничения

- **Слой D никогда не на hot-path.** Падение Loki / аналитики / автомата не влияет
  на латентность, доступность и решения каскада. Эдж — fail-stale.
- **Ни одно изменение enforcement не происходит без человека.** Автомат готовит
  draft-PR; merge — ручной. Прямого пути «аналитика → блокировка» нет.
- **Все обратимо.** Любой переход откатывается `demote-fp.sh` (адресно) или
  `git revert` (PR целиком), в рамках SLA доставки.
- **Блокировка только после наблюдения.** Между прогнозом и enforcement всегда
  есть observe-only фаза на живом трафике; активация — по факту, не по прогнозу.
- **Чего слой D НЕ умеет (намеренно):**
  - не блокирует общие fp инструментов (intent-правило) — это работа
    `ua_blacklist`/`ip_blocklist`, решает человек;
  - не вводит enforced-TTL на эдже (контракт каталога не меняется);
  - не работает с прод-prod-edge (Channel C на стенде = git→backend→эдж);
  - `unknown`-записи (без истории наблюдения) автомат не снимает — оставляет
    человеку.

## Зоны ответственности

| Кто | Что делает в слое D |
| --- | --- |
| **Аналитика (producer)** | читает Loki, считает score/gates, пишет артефакты, шлет отчет |
| **Автомат** | готовит один draft-PR/сутки в обе стороны; никогда не мержит |
| **Оператор (человек)** | ревьюит и мержит PR; адресно promote/demote; решает кейсы intent=false |
| **Продакт** | правит slow-каталоги (`ua_blacklist`/`ip_blocklist`/…) через PR по CODEOWNERS |
| **Каскад (эдж)** | исполняет доехавший каталог; эмитит BAC_LOG; матчит staging observe-only |

## Что не входит

- UI/дашборд для просмотра кандидатов и аналитики клиентом — отдельная задача.
- Enforced-TTL и любые изменения контракта каталога/каскада.
- Боевой деплой на prod-edge / salt-pillars / Puppet прода — зона CDN operator-админов и
  будущих фаз ([vision.md](vision.md) Roadmap, Phase 3+).
- Поведенческий ML на сессиях (L6/L7) — другой продукт.
