# API и Account Protection — спецификация (пост-MVP)

**Версия:** v1.0 · Статус: проектный контракт (целевое поведение) · слой пост-MVP

Этот документ описывает целевое поведение слоя защиты API и аккаунтов как отдельный
слой поверх каскада ([vision.md](vision.md)): спецификация «бери и делай», по которой
строится реализация. Каскад из vision лимитирует и проверяет по сетевым ключам
(IP, fp, UA, путь); этот слой добавляет измерение идентичности (аккаунт, ключ,
токен) и контракта API (что разрешено на эндпоинте), которых у каскада нет.

**Сопутствующие материалы (как у vision):**
[api-rules-reference.md](api-rules-reference.md) — правила в формате «если условие →
вердикт»; [api-entities-reference.md](api-entities-reference.md) — словарь сущностей
(стадии, ключи, профили, каталоги, теги, поля лога, перечисления);
[api-config-templates.md](api-config-templates.md) — структура policy-полей, формат
каталога схем, JWT/mTLS-конфиг.

---

## 1. Что это

Слой покрывает две близкие, но разные оси защиты API:

- **Ось A — abuse аккаунтов и API.** Credential stuffing, brute force, массовая
  фейковая регистрация, scraping, перебор и утечка ключей, enumeration. Контроль по
  идентичности и квотам.
- **Ось B — контракт и governance.** Позитивная модель: что разрешено на эндпоинте
  (метод, тип, схема, токен), и отсечение всего прочего; ресурсные лимиты,
  edge-валидация токенов, транспортная гигиена, инвентаризация эндпоинтов.

Оси комплементарны и делят один фундамент — декларацию эндпоинтов и извлечение
идентичности (см. §4).

**Позитивная модель (ось B) ↔ негативная модель WAF.** Ось B описывает, что
**разрешено**, и режет остальное; WAF ([waf-spec.md](waf-spec.md)) ищет сигнатуры
конкретных атак. Это два дополняющих подхода к одной поверхности.

## 2. Зачем — чего не хватает каскаду

Каскад уже умеет rate-limit по сетевым ключам, репутацию и challenge. Этого мало:

- **Стаффинг, размазанный по тысяче IP**, но бьющий в один аккаунт — per-IP лимит
  обходится ротацией прокси/ботнетом.
- **Abuse одного API-ключа с многих IP** — сетевой ключ не видит «ключ».
- **Targeted brute force одного аккаунта** — нужен счетчик по аккаунту.
- **Контракт API не проверяется** — нет валидации метода/типа/схемы на эндпоинте,
  лимитов размера и сложности тела, edge-валидации токена, security-заголовков,
  инвентаря эндпоинтов.

Нужен контроль по идентичности (аккаунт/ключ/токен) и по контракту запроса, которого
у каскада сейчас нет.

## 3. Ключевое ограничение: эдж identity-blind

Каскад видит IP, fp, UA, Host, путь, заголовки — но не «какой аккаунт» и не «какой
ключ». Поэтому фундамент оси A — стадия извлечения идентичности, которая кладет
нормализованный ключ в контекст запроса, ровно как rate-limit по fp кеит на fp. Без
нее ось A не строится.

Второй сквозной принцип: сильнейший сигнал auth-абьюза — доля неуспешных логинов,
а ее эдж видит только из ответа origin (статус 401/403 в response-фазе). Это тот же
паттерн обратной связи, что challenge solve-rate в слое аналитики
([analytics-spec.md](analytics-spec.md)).

## 4. Где в каскаде

```
hygiene → [contract] → [schema] → reputation → tls_fp → [identity-extract] →
          rate_limits(+per-key) → [JWT] → verification
   ↑ resource-limits (часть nginx до Lua, часть Lua после парса)
   ↑ mTLS — транспорт, до каскада
   ↓ transport-гигиена — response/header-фаза
   ↓ failed-auth feedback, API inventory — log/response-фаза, аналитика
```

Точное размещение стадий фиксируется при реализации; принцип: контракт и схема рано
(дешево отсекают мусор до дорогих слоев), извлечение идентичности перед rate_limits,
валидация токена перед проксированием на origin. Стадии идентичности и контракта
активны только на путях, объявленных в декларации эндпоинтов (§5.1).

---

## 5. Ось A — abuse аккаунтов и API

### 5.1 Декларация эндпоинтов (фундамент)

Per-host декларация: пути логина, регистрации и API (glob-паттерны), плюс
опциональные per-endpoint квоты. Эдж дает классификатор «какой класс у этого пути».
Это компаньон-фундамент: стадии идентичности и контракта работают только на
объявленных путях, на остальных — skip. Доставляется per-host через политику
(тот же путь, что и прочая per-host конфигурация).

### 5.2 Извлечение идентичности (фундамент)

На объявленных auth/API-путях извлекает: API-ключ или bearer-токен из заголовка
авторизации / `X-API-Key` / query; username из формы логина (form-urlencoded / JSON).
Нормализует в ключ для rate-профилей и репутации.

**PII и безопасность (жесткий инвариант):**

- username и токен/ключ хешируются (HMAC) перед использованием как ключ и в логах —
  никогда не сырьем.
- Пароль никогда не логируется, не хранится и не инспектируется — его значение слою
  не нужно.
- Чтение тела включается только на login-путях, с лимитом размера (§6.3) и bypass
  для крупных/upload-эндпоинтов.

### 5.3 Per-credential / per-key rate-профили

Новые GCRA-профили поверх существующего rate-limit-движка (те же окна и
shared-memory ячейки), но ключ — идентичность, а не сетевой параметр:

- профиль по hashed-username — ловит стаффинг по многим аккаунтам и brute force
  одного аккаунта;
- профиль по hashed-ключу — ловит abuse одного ключа с многих IP, scraping,
  enumeration, утечку ключа.

Graceful skip при отсутствии ключа (как guard при промахе fp-кеша). Enforcement
mode-gated: финальное действие (challenge или 429) зависит от режима и строгости
хоста, как у существующих rate-правил.

### 5.4 Failed-auth feedback

Обратная связь из ответа origin (log/response-фаза): читает upstream-статус на
login-путях, классифицирует успех/неуспех (401/403 = неуспех), копит долю неуспешных
по hashed-аккаунту и по /24-подсети. Всплеск доли неуспешных → +score в репутацию и
эскалация challenge/строгости на последующих запросах источника.

Это статистика ответов, не проверка валидности пароля. Зависит от того, что origin
отдает различимые статусы на успех и неуспех — допущение фиксируется при внедрении на
конкретном домене.

### 5.5 Disposable-email / breached-cred (опционально)

Сигнал для стаффинга и фейк-регистрации. Реалистичный edge-скоуп — каталог
disposable-email доменов (доставляется как slow-каталог, PR-only). Полноценная
проверка пароля по брешь-листу — backend-функция, не hot-path: эдж пароль не
валидирует.

## 6. Ось B — контракт и governance

### 6.1 Per-endpoint contract (позитивная модель)

Поверх глобального method-whitelist гигиены — позитивная модель по эндпоинту:
разрешенные методы, разрешенные content-type, опциональные обязательные параметры;
все прочее → reject. На путях без правил — skip. mode-gated (shadow по умолчанию),
тег `api:contract_violation`.

### 6.2 Schema-валидация

Поверх контракта — валидация тела против JSON-схемы (компилированное подмножество
OpenAPI, не полный движок в hot-path): типы, обязательные поля,
`additionalProperties=false` (отсекает mass-assignment-вектор на входе). Схемы —
slow-каталог, PR-only. Требует чтения тела с лимитом (§6.3) и bypass для upload.
Тег `api:schema_violation`.

### 6.3 Resource limits

Защита от «тяжелого» одного запроса, который не ловит rate-лимит по числу:

- размер тела — per-host/per-endpoint (часть на уровне nginx, до Lua);
- структурная сложность JSON — максимальная глубина и длина массивов (защита от
  «billion laughs»);
- GraphQL (опционально) — глубина, стоимость, число алиасов.

Дополняет лимит одновременных соединений из DDoS-слоя ([ddos-spec.md](ddos-spec.md)):
там — соединения, тут — стоимость одного запроса.

### 6.4 Edge JWT/token-валидация

Идентичность извлекла токен как ключ; здесь проверяется его валидность на API-путях:
подпись (JWKS или секрет), `exp`/`nbf`, `iss`/`aud`. Форжед или протухший токен
режется до проксирования на origin (разгрузка backend + ранний блок). Ключи и JWKS
доставляются как секрет/каталог. Опциональный required-scope per-endpoint = coarse
authz. Тег `api:token_invalid`.

Это аутентификация токена, не авторизация объекта: владение объектом по ID (BOLA) и
полный BFLA — backend. Только stateless-проверка; ревокация и интроспекция со state —
тоже backend. Сырой токен не логируется.

### 6.5 mTLS / client-cert (опционально, per-tenant)

Для API с сильной клиентской аутентификацией: проверка клиентского сертификата на
mTLS-хостах. Транспортный уровень, до каскада. По умолчанию выключено. Совместимость
с on-demand TLS проверяется отдельно. Тег `api:mtls_fail`.

### 6.6 Transport-гигиена

Response-side, дешево и с высоким ROI, per-host: security-заголовки (HSTS,
X-Content-Type-Options, корректный CORS по политике — не `*` вслепую); срезка
banner-заголовков и версий сервера; маскировка многословных 5xx-ошибок origin.

### 6.7 API inventory / governance

Аналитика поверх лога: эдж логирует весь трафик и знает объявленные пути → diff
вызываемых и объявленных эндпоинтов дает инвентаризацию почти бесплатно:
undeclared (shadow, тег `api:shadow_endpoint`) и declared-but-unused (zombie).
Сюда же — enforcement устаревших версий (deprecated-путь → 410, mode-gated).

---

## 7. Enforcement: для API нет JS-challenge

JS-challenge браузерный — на чистых API-путях на него полагаться нельзя. Опора
enforcement здесь: rate-лимиты по ключу/аккаунту, валидация токена/mTLS, репутация,
429/4xx по контракту. Для login-путей с браузерным клиентом step-up через challenge
уместен.

---

## 8. Что переиспользуется из каскада

- **Rate-limit-движок** (GCRA + keying) — для per-key/per-account профилей.
- **Per-host политика** — для декларации эндпоинтов, контракта, JWT/mTLS-конфига,
  transport-флагов.
- **Доставка slow-каталогов** (PR-only) — для схем, disposable-email доменов, JWKS.
- **Репутация и challenge** — per-key/per-account рядом с per-IP, step-up на auth.
- **Лог и теги** — для сигналов осей (`account:*`, `api:*`) и инвентаря.
- **glob-матчинг путей** — для классификации эндпоинтов.

## 9. Технические границы (backend, не эдж)

Эти сценарии не решаются на эдже — им нужен контекст, которого у эджа нет. Эдж
дает сигнал, не решение:

- **ATO** (аномальный успешный вход) — нужна история аккаунта; эдж дает лишь
  fp/geo-контекст.
- **Авторизация объектов/функций** (BOLA, полный BFLA), mass-assignment в семантике,
  бизнес-логика, контроль PII-в-ответах — нужны identity + ownership + бизнес-правила.
- **Credential stuffing** на эдже = объем + доля неуспешных + bot-score, не проверка
  пароля по брешь-листу.
- **Breached-password validation**, ревокация/интроспекция токена — backend-функции,
  не hot-path.

## 10. Зоны ответственности

| Кто | Что делает |
| --- | --- |
| **Эдж (каскад)** | извлекает идентичность, лимитирует по ключу/аккаунту, валидирует контракт/схему/токен/mTLS, гигиена ответов |
| **Аналитика лога** | failed-auth feedback, инвентаризация эндпоинтов, draft-PR кандидатов в декларацию |
| **Политика (per-host)** | декларация эндпоинтов, контракт, JWT/mTLS-конфиг, transport-флаги |
| **Backend** | ATO, авторизация объектов/бизнес-логика, breached-password, ревокация токенов |

## 11. Состав и порядок внедрения

| Компонент | Ось | Зависит от |
| --- | --- | --- |
| Декларация эндпоинтов | фундамент | — |
| Извлечение идентичности | фундамент | — |
| Per-key/per-account rate-профили | A | оба фундамента |
| Failed-auth feedback | A | идентичность + декларация |
| Disposable-email сигнал (опц.) | A | идентичность |
| Per-endpoint contract | B | декларация |
| Resource limits | B | — |
| Schema-валидация | B | contract + resource limits |
| Edge JWT-валидация | B | идентичность |
| Transport-гигиена | B | — |
| mTLS (опц.) | B | — |
| API inventory | B | декларация |

Порядок: два фундамента (декларация + идентичность) параллельно → per-key профили,
failed-auth, contract; дешевые/ранние (resource limits, transport-гигиена) — в любой
момент → schema, JWT, inventory. Разбор правил — в
[api-rules-reference.md](api-rules-reference.md).

## 12. Что не входит

- Авторизация объектов/функций и бизнес-логика (backend).
- Полная проверка пароля по брешь-листу, ревокация токенов со state (backend).
- Сигнатурный поиск атак (SQLi/XSS/…) — это WAF ([waf-spec.md](waf-spec.md)),
  негативная модель, комплементарная позитивной модели оси B.
