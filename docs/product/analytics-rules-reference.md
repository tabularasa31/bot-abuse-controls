# Аналитика и блок-лист — справочник правил

Правила слоя аналитики в формате «если условие → действие». Контракт поведения —
[analytics-spec.md](analytics-spec.md); словарь сущностей —
[analytics-entities-reference.md](analytics-entities-reference.md).

Группы правил: скоринг (ранжирование), гейты (допуск-вето), жизненный цикл (переходы
записи), автомат, anti-poisoning. Плюс справочники-источники (каталоги), на которые
опираются скоринг и гейты.

---

## 1. Скоринг (ранжирование, аддитивно)

Каждое сработавшее правило добавляет очки. Сумма ранжирует кандидатов; сама по себе
ничего не блокирует. Тиры: HIGH ≥5 · MEDIUM 3–4 · LOW 1–2.

| # | Если | → очки | Тип |
| --- | --- | --- | --- |
| S1 | UA называет браузер, но хеши отпечатка — из словаря инструментов автоматизации (маскировка) | **+3** (impersonator) | сигнатура |
| S2 | UA браузерный И число шифров вне браузерного набора | +1 (suspicious cipher) | эвристика |
| S3 | UA — инструмент (curl/python/go/okhttp/bot/scanner) | +1 (automation UA) | сигнатура |
| S4 | хотя бы один IP отпечатка в datacenter-ASN | +1 (DC ASN) | контекст |
| S5 | ≥2 разных IP под отпечатком | +1 (multi-IP) | контекст |
| S6 | отпечаток виден в ≥2 разных календарных дня | +1 (persistent) | контекст |
| S7 | под отпечатком есть обращения к recon-путям (`/.env`, `/wp-login`, …) | +1 (recon URI) | поведение |
| S8 | хеши отпечатка совпали с headless-записью в `tls_fp_catalog` (Playwright/Puppeteer/UCD) | **+3** (headless) | сигнатура |
| S9 | UA называет версию браузера, не совпадающую с версией по позитивному каталогу (UA↔fp mismatch) | **+2** (version mismatch) | сигнатура |
| S10 | ритмичные межзапросные интервалы / навигация по recon, не по ссылкам | +1 (behavioral) | поведение |

> Веса: словарные/каталожные совпадения (S1, S8) весят +3 — точные сигнатуры.
> S9 весит +2 — точный, но свежий релиз браузера может временно разойтись с каталогом.
> Слабые эвристики (S2, S10) — +1.

## 2. Гейты (допуск — пороги-вето, НЕ складываются)

Score может быть любым; если хоть один гейт не пройден — промоута нет. Гейты — про
безопасность блокировки (не заденем ли невиновных под тем же отпечатком), а не про то,
бот ли это (это считает score).

| # | Если | → действие | Категория |
| --- | --- | --- | --- |
| G1 | событий меньше минимума ИЛИ нет ни одного IP | не промоутить (шум) — ручной форс может перебить | volume |
| G2 | хотя бы один allow-вердикт под отпечатком ИЛИ IP в whitelist | **вето: не промоутить** (легит/verified) | allowlist (вето) |
| G3 | отпечаток уже есть в каталоге | не промоутить (идемпотентность) | dedup |
| G4 | НЕ (impersonator ИЛИ (recon И не generic_honest_tool)) | **вето: не авто-промоутить** (общий отпечаток инструмента) | обоснованность (intent, вето) |
| G5 | отпечаток есть в каталоге настоящих браузеров | **вето: никогда не блокировать** (реальный браузер, под ним живые люди) | known-good / настоящий браузер (вето) |
| G6 | по отпечатку выдано достаточно challenge И они решаются (доля решений НЕ ≈ 0) | **вето: не блокировать** (под отпечатком люди); низкая доля решений, наоборот, ускоряет `staging → active` (см. L2) | challenge-solve-rate (вето) |

> G5 (известно-хороший браузер) — и есть защита «под отпечатком живые люди»: «живые люди
> под сигнатурой» = её fp есть в каталоге браузеров (блок идёт по точному fp), отдельной
> проверки доли не нужно. G4 закрывает другой риск — «заблокировали общий отпечаток
> инструмента». G6 двусторонний: решаемые challenge — вето (люди),
> нерешаемые — ускорение к блоку; счёт только по событиям с хоста в режиме `active` и
> attack-off (под attack mode эдж челленджит всех подряд; логи без поля attack_mode — тоже
> не в счёт, консервативно).

## 3. Справочники-источники (каталоги)

Скоринг и гейты опираются на справочники. Аналитический воркер сам наполняет (draft-PR)
только `tls_fp_blocklist`. `tls_fp_browser_profiles` (браузеры) и `tls_fp_catalog`
(инструменты) наполняет харвестер отпечатков (см. §7), снимая fp с реальных клиентов; хеши
не пишут руками. Headless-отпечатки — записи в том же `tls_fp_catalog`, отдельного каталога
нет. Новый незнакомый отпечаток из логов атрибутирует человек (ручное расследование).

| Справочник | Что дает | Кормит |
| --- | --- | --- |
| словарь инструментов (`tls_fp_catalog`) | хеши инструментов (curl/python/go/okhttp) и headless-стэков (Playwright/Puppeteer/UCD) | impersonator (S1), automation UA (S3), headless (S8), обоснованность (G4) |
| позитивный каталог браузеров (`tls_fp_browser_profiles`) | белый список реальных браузеров: `полный fp → {семейство, версия}` | known-good / настоящий браузер (G5), version mismatch (S9) |
| challenge issued/solved | счетчики выданных/решенных challenge по fp | challenge-solve-rate гейт (G6), ускорение `staging → active` |

## 4. Жизненный цикл записи блок-листа

| # | Если | → действие |
| --- | --- | --- |
| L1 | тир HIGH И достаточно дней И все гейты И обоснованность (auto_eligible) | promote: PR со статусом `staging` |
| L2 | запись в `staging` ≥ окна наблюдения И матчей ≥ минимума И fp не в каталоге браузеров И нет allowlist-хитов | activate: PR `staging → active` |
| L3 | запись в `staging`, но fp попал в каталог браузеров (харвестер подтвердил) ИЛИ среди матчей allowlist (fp_caught) | НЕ активировать; флаг demote/remove |
| L4 | запись в `staging`, матчей/времени мало (observe) | оставить в `staging`, наблюдать дальше |
| L5 | запись `active` молчит дольше TTL | demote: `active → staging` |
| L6 | запись `staging` (после demote) снова молчит дольше TTL | remove: удалить из каталога |
| L7 | запись в каталоге без истории наблюдения, молчит | НЕ трогать автоматом — оставить человеку |
| L8 | оператор подтвердил ложный блок | demote адресно (`active → staging` или remove), обратимо |

## 5. Автомат (draft-PR)

Прогон — суточный (cron): ротация состояния → скоринг (отчет + артефакты решений) →
автомат собирает созревшее в один draft-PR. Автомат сам каталог не правит вне PR и не
мержит.

| # | Если | → действие |
| --- | --- | --- |
| A1 | за прогон есть созревшие promote/activate/demote | собрать ВСЕ в один draft-PR (батч) |
| A2 | за прогон ничего не созрело | PR не открывать (no-op) |
| A3 | для текущего периода уже есть открытый PR | пропустить (идемпотентность) |
| A4 | артефакты решений старше порога свежести | НЕ действовать (воркер мог лечь) — выйти |
| A5 | любой сбой посреди применения правок | откатить правки каталога, вернуться к базе |
| A6 | PR собран | оставить **draft**; человек ревьюит и мержит — автомат НЕ мержит |

## 6. Anti-poisoning

| # | Если | → действие |
| --- | --- | --- |
| P1 | злоумышленник льет «человеческий» трафик под своим fp | бесполезно: «настоящий браузер» берется из каталога (харвестер с реальных браузеров), а не из трафика — отравить нечего |
| P2 | отпечаток совпал с каталогом настоящих браузеров (known-good) | никогда не авто-блок (см. G5) |
| P3 | бот в точности копирует TLS-рукопожатие реального браузера | известный предел: его fp попадет в каталог браузеров и уйдет от автоблока (продвинутые мимикрирующие боты — не наш случай) |

## 7. Харвестер отпечатков

Наполняет `tls_fp_browser_profiles` (браузеры) и `tls_fp_catalog` (инструменты/headless).
Отдельный продьюсер, как автомат: сам каталоги не правит вне draft-PR, не мержит.

| # | Если | → действие |
| --- | --- | --- |
| F1 | по расписанию (cron-one-shot) | гонит известный набор — браузеры (Chrome/FF/Edge) и инструменты (curl/python/go/okhttp/headless) — на `/__fp`, снимает полный fp |
| F2 | собран срез по браузерам | draft-PR в `tls_fp_browser_profiles` (allowlist); мержит человек |
| F3 | собран срез по инструментам/headless | draft-PR в `tls_fp_catalog` (`hash → family`); мержит человек |
| F4 | запись в `tls_fp_browser_profiles` смержена как `staging` | для allowlist это «уже доверяем» → сразу гасит mismatch-флаг (инверсия vs blocklist-staging) |
| F5 | клиент, которого харвестер не даёт (LibreWolf/Tor/mobile/экзотика) | ручная запись (PR) |
| F6 | в логах частый отпечаток, не давшийся ни одним прогоном | НЕ авто; ручная атрибуция человеком |

Каденс — по реальному дрейфу TLS (у Chrome задаёт BoringSSL): порядка раза в несколько
мажоров, не ежемесячно.

---

## 8. Инвариант

Единственный способ изменить enforcement — merged PR в каталог блок-листа.
Скоринг, гейты и автомат только предлагают (draft-PR); вердикт на трафике
выносит каскад по доставленному каталогу. Прямого пути «аналитика → блокировка» без
merged PR и человека нет.
