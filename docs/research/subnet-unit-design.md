# Дизайн #3 — subnet как единица анализа (+ авто-attack-mode)

> **Статус: ПЛАНИРУЕТСЯ / design draft.** НЕ реализовано. Развивает идею #3 из
> [bot-detector-roadmap.md](bot-detector-roadmap.md). Опирается на D1 (per-fp scoring),
> C7 (attack_mode), B10/B11 (per-host policy), reputation/geoip (asn/hosting).

## Идея в одну строку

Поднять единицу анализа выше отдельного fp. fp злоумышленник ротирует дёшево (новый JA4
проскакивает под per-fp порогами D1), но **пул IP сменить дорого** — он заперт в своём /24
датацентра. Агрегируя по subnet, видим сигнатуру ротации (много короткоживущих fp с одного
пула) и реагируем на уровне пула.

## Что уже есть (не greenfield)

- Зрелый **per-fp pipeline** (D1): score + gates + staging + promote.
- Данные по сети собираются: `enrich_ips` (asn/hosting), `geoip.lua`, каталог `asn_datacenters`,
  `ip_blocklist` CIDR-aware (`lua-resty-ipmatcher`) + Channel C.
- **`find_asn_watch_candidates`** ([analyze.py](../../infra/demo-stand/scripts/analyze.py)) —
  ASN-агрегация, но **report-only и грубая** («все события bot-like И ≥2»), считает `n_fps`, но
  ничего с ним не делает; помечена «ASN-level challenge, **not hard block**». Ротацию *видит*,
  не *действует*.

## Сквозной принцип (итог обсуждения)

> Постоянно — только мягко (репутация → баллы/challenge) и только по датацентрам; жёстко
> (drop) — лишь на время атаки, по узкому пулу, с авто-снятием, и лишь когда challenge уже не
> окупается. **Никаких persistent IP-блок-каталогов** (IP — общий/переназначаемый ресурс,
> persistent-блок протухает в ложняки).

## Как отличаем DC-пул от «человеческого» (общее для обеих фаз)

Асимметрично, в пользу осторожности (ошибочно принять резидентный пул за DC = агрегировать
живых людей):
- **Главный гейт — каталог `asn_datacenters`** (кураторский, PR, доверенный). Только он = «DC
  железно».
- **Флаг `hosting`** из `enrich_ips` (ip-api) — НЕ автогейт, а **поставщик кандидатов**:
  аналитика предлагает новые хостинг-ASN в каталог (отчёт / draft-PR), человек подтверждает.
- **Смешанные ASN** (хостинг+резидент у одного провайдера) — ASN-уровню не доверяем, требуем,
  чтобы **сам /24 прошёл пороги** (ротация/recon/0-human).
- **Единица действия — /24 (v4)**, ASN — только DC-классификатор и контекст. **IPv6 —
  отдельно и консервативно** (у DC /48, у резидента /56–/64 на домохозяйство → Phase 1 = v4-only).

## Фаза 1 — «тихая репутация пулов» (always-on, soft, никого не блокирует)

**Алгоритм решения по /24** (медленный аналитический цикл, по логам из Loki):

```
1. Это датацентр? (asn_datacenters; смешанные → судим по самому /24)
     нет  → СТОП, пул не оцениваем (за резидентным /24 — живые люди)
     да   → дальше
2. Похоже на бот-ферму? три признака:
     • ротация отпечатков — много разных fp с одного пула (n_fps/churn)
     • почти никто не проходит человеческую проверку (human_share ≈ 0)
     • много recon-URI (/admin, /.env, …)
3. Признаки есть → пул помечается «подозрительный» (репутация):
     (C) каждый fp из пула получает +score в per-fp pipeline (усиление D1)
     (B) опц. посетителям пула охотнее показываем challenge (Strictness↑)
   Признаков нет → ничего.
```

**Гарантии:** никаких блокировок (макс — одна капча реальному юзеру), только DC, обратимо
(пул замолчал → репутация сходит на нет, как auto-demote у fp).

**Выход:** медленно обновляемый список «подозрительных DC-пулов» (артефакт аналитики, отдаётся
через Channel C как `subnet_reputation`).

## Фаза 2 — «жёстко, но только в атаке» (transient, авто-снятие)

Зависит от того, что хост **в attack_mode** (вручную или авто — см. ниже). Решение —
**эдж-реактивное** (дневной цикл слишком медленный для «в моменте»).

**Алгоритм решения по DC-/24 во время атаки:**

```
1. Пул под атакой получает обычную реакцию — challenge.
2. Эскалация challenge → DROP только если challenge перестал окупаться:
     (а) challenge-rate пула упёрся в бюджет CPU/полосы эджа (volumetric); ИЛИ
     (б) solve_rate пула ≈ 0 ПРИ issued >= MIN_SUBNET_CHALLENGES (D12-guard): тысячи
         выдач, решено ≈ноль → жжём CPU впустую
3. DROP — на короткий TTL:
     • сам снимается по TTL / окончании атаки
     • runtime-state (shared_dict), НЕ запись в каталог, ручной чистки нет
```

**Min-порог перед solve_rate (review).** Критерий (б) применяется только при `issued >=
MIN_SUBNET_CHALLENGES` — иначе 1-2 нерешённых challenge с тихой легит-подсети дали бы формальный
`solve_rate≈0` и ложный DROP. Тот же асимметричный guard, что в D12 (`MIN_CHALLENGE_ISSUED`).
Критерий (а) — volumetric — на малых N и так не срабатывает.

**Защита памяти эджа (review).** Распределённая ротация по огромному числу /24 могла бы
переполнить `shared_dict` (shared memory exhaustion). Поэтому: жёсткий **cap на число
одновременно отслеживаемых подсетей** + **LRU-вытеснение** (ngx shared dict вытесняет LRU при OOM,
но cap делаем явным для предсказуемости). Вытеснение безопасно: упавший из трекинга /24 просто
вернётся к обычному challenge (не к DROP) — fail-open в сторону мягкости. Перекликается с D7
(bound growth state).

**Прайор:** список из Фазы 1 пред-взводит горячие /24 (порог ниже, реакция быстрее при флипе
attack_mode).

**Как узнаём, что challenge стал нагрузкой (Q1):** rate `antibot_challenge_issued_total` (C5) ×
стоимость vs бюджет эджа + `cascade_ms` (BAC_LOG timing); и `solve_rate≈0` по пулу (D12) —
формальный сигнал «challenge тут только нагрузка». Оба наблюдаемы в метриках/Grafana.

**Гарантии:** жёсткое живёт минутами не вечно; challenge всегда первым, drop — fallback; только
DC; никаких protухающих IP-списков.

## Зависимость — авто-attack-mode (отдельный тикет)

Ручной тумблер attack_mode — слабое место (атака ночью, клиента нет → Фаза 2 не включилась).
Авто-детект атаки поднимает режим за клиента, **под явным разрешением клиента**.

**Новый per-host флаг `auto_attack_mode`** (в policy, рядом с `attack_mode`; Channel C + dashboard
PATCH, как C7/B10):
- **`false` (дефолт, консервативно):** attack_mode меняем НЕ сами, только по прямому включению
  клиента. **Но детект работает всегда → алертим:** «обнаружили атаку — включите attack_mode или
  дайте нам право включать самим».
- **`true`:** при детекте сами поднимаем attack_mode (гистерезис + авто-снятие), override клиента
  сохраняется.

**Детект — на «плохом» трафике, НЕ на голом объёме** (чтобы не наказать флеш-крауд живых людей),
относительно базлайна хоста:
- всплеск bot-like вердиктов / challenge-выдачи;
- `solve_rate` хоста падает в пол (D12);
- **origin в стрессе** — растут `upstream_response_ms`/`proxy_ms` (timing-поля BAC_LOG уже есть).

**ВКЛ и ВЫКЛ — на РАЗНЫХ сигналах (review, защита от осцилляции):** origin-стресс годится только
как сигнал **ВКЛ**. Снимать режим по нему НЕЛЬЗЯ: как только защита включилась, нагрузка на origin
спадает, его метрики нормализуются → система решит «атака кончилась» → выключит → атака снова бьёт
в origin → on/off-осцилляция. Поэтому **ВЫКЛ — строго по эдж-метрикам**: объём bot-like/
challenge'ируемых/дропнутых запросов упал ниже порога и держится cooldown-окно. origin-health в
решении о снятии не участвует.

**Кто включил — тот выключает:** авто-поднятое авто-снимаем после затишья (по эдж-метрикам выше);
ручное клиента не трогаем; ручное действие всегда главнее авто. Помечаем «источник» текущего
attack_mode (auto vs manual) — прецедент различения «кто/когда» есть в C7 (clearance pre/during-attack).

**Скоуп:** авто-attack-mode полезен ВСЕМУ attack-пути (C4/C5/C7 завязаны на attack_mode), а не
только Фазе 2 → отдельный тикет, Фаза 2 — его потребитель.

## Разбивка на тикеты

- **[D14] #3 Phase 1** — subnet-репутация (soft, аналитика): DC-гейт, /24-агрегация
  churn/human_share/recon, +score в fp, апгрейд `find_asn_watch_candidates`, опц. soft-Strictness
  через Channel C `subnet_reputation`. Не трогает attack-путь.
- **[D15] #3 Phase 2** — transient subnet challenge→drop под атакой: эдж-реактивные /24-счётчики,
  гейт attack_mode, эскалация по бюджету/solve_rate, TTL+авто-снятие, прайор из D14. Зависит от D16.
- **[D16] авто-attack-mode** — адаптивный детект атаки (плохой трафик + origin-стресс), флаг
  `auto_attack_mode` (дефолт off) + алерт при off, авто-вкл/выкл с источником, override клиента.

## Честное ограничение (обе фазы)

Закрывает **дешёвую датацентровую fp-ротацию**, но **НЕ резидентные прокси-сети** (IP размазаны
по тысячам легит-резидентных ASN специально против IP-репутации; под DC-гейт не попадают). Это
территория #1 (challenge/solve-rate) и #4 (поведение), не subnet-юнита.

## Не входит / Phase-границы

- Persistent CIDR-блок в `ip_blocklist` как авто-механизм — **отвергнут** (protухание).
- IPv6-юнит — консервативно отдельно (Phase 1 = v4).
- Поведение во времени (ритм/навигация) — это #4, не #3.
